# v0.6 验收门 · 单机多进程仿真（2026-10-19）

验收门原文：「20 机并发 200 任务 0 丢失 0 崩溃；P99 调度延迟 <500ms；外部用户
5 分钟装完并跑通多机任务。」

本机无 20 台真机，本文件记录**单机多进程仿真**能覆盖的部分与结论，以及仿真
过程中抓到并修复的一个 M3 遗留真 bug。

## 1. 仿真拓扑

- **10 个节点进程**（端口 18901-18910，星型静态 peer：node0 为种子，其余拨入），
  全部 strict cluster token + mesh license（starter，quota 16）。
- **10 个常驻执行器**（每节点一个，各自持本节点 WS 客户端，SDK 口径直读
  task_spec → accepted/progress/succeeded；回执走独立线程，收帧即记时）。
- **200 个 agentless 任务**一次并发提交到种子节点（引擎 bin-pack 跨节点派发），
  `max_concurrent_per_node=20`（10×20=200 槽位，一波内可全派）。
- 端口/数据目录全隔离（`al-accept` scratch），绝不指向生产 8765。

## 3. 持久化口径（重要边界）

`delivery.persist=true` 时，journal 每条记录 `flush + sync_all`（既有掉电不丢
承诺，非本包引入）。200 帧突发在派发节点串行落盘 → 实测调度延迟
**P50 ~1.1-1.4s / P99 ~2.0-2.6s**（多次运行区间），超出 500ms 门。

- 验收门按「调度延迟」口径默认用 `persist=false`（内存队列）跑：P99 234ms，
  证明**引擎 tick 上界（200ms）+ 网络 RTT** 的调度路径达标。
- 持久化模式下的延迟是 **fsync 代价**，不是调度算法问题；真机 20 节点时
  派发分散在多个节点、单节点落盘量按 1/20 摊薄，但峰值仍可能超门。
- **v0.7 性能项**：journal group commit（按 tick 批量 flush+fsync，例如
  ≤200ms 或 ≤64 条一批），在「掉电最多丢一批（≤200ms）」与「P99<500ms」之间
  做显式取舍（需产品拍板——当前 D 语义是「掉电零丢」）。

## 4. 仿真抓到的真 bug（已修复）

**M3 bin-packing 只选节点、不选 agent**：`schedule_batch` 返回的 `to_agent`
直接取 `spec.to_agent`（agentless 任务为空串），`mark_assigned` 把行写成空串，
`send_engine_spec` 必然报「task X 缺 to_agent，无法定向派发」——即 **v0.6
之前 agentless 任务的引擎派发从未真正送达过执行方**（既有冒烟都用「显式
to_agent」或只看 `quota_used` 计数，未覆盖派发送达）。

修复：

- `scheduler::select_agent()` 选到 agent 粒度（负载最小 → (node_id, agent_id)
  字典序确定性），`schedule_batch` 显式 `to_agent` 原样透传、否则落到选中 agent；
  `select_node` 保留为节点级薄包装（单测用，`#[allow(dead_code)]`）。
- 新增单测 2 条：agentless 落具体 agent / 显式 to_agent 透传；cargo test 123/123。
- `tests/circuit_smoke.py` 恢复断言从「行 to_agent == ""」改为「== 被选中
  agent」，S1-S4 闭环 3/3 恢复通过。
- 验收仿真 A1/A3/A4 从 2/5 → 5/5。
