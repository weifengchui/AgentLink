# warmpool 预热池验证（2026-10-19）

v0.6 P2 收官条目：「预热池形式化：常驻桥 = agent warmpool，任务到达即注上下文，
冷启动 <200ms【§5.3】」。设计案原文在盘外（仓库内唯一定义句在路线图 L39；
`docs/task引擎内核化设计-2026-10-18.md` L208 的开放问题「是否内置自动拉起
本机 executor 桥」即在问这件事），本包按仓内可确证语义形式化。

## 1. 形式化语义

**池 = `engine.warmpool.members` 显式名单；池位 = 成员 agent；keep-warm =
引擎周期的预热任务派发循环。**

- 引擎每 `interval_secs`（下限 5s）对每个**在线且未熔断**的成员检查在池任务
  数（状态 Pending/Running 且 type=`task_type` 且 `to_agent`=该成员）；低于
  `keep_inflight` 就注入一行预热任务（type=`warmup.ping`，correlation=
  "warmpool"，priority=900，定向成员所在节点），入库走 `apply_task_spec`
  （与 POST /v1/tasks 同一内核口径）+ `send_engine_spec` 直投。
- 常驻桥（Adapter SDK 适配器 / 现役 executor / hermes 桥）收到 warm-up 任务
  no-op 秒回 → 桥进程与会话**保持常驻**；真实任务到达时 tick（200ms 上界）
  内即可派给已热的执行方 —— 「任务到达即注上下文」的完整路径。
- 在线判定用 `Router::agent_online`（本地注册与船队缓存同优先序，按 online
  判定；不复用 find_agent_node 它对本机注册不滤 online——冒烟 S5 验证此坑）。
- 默认关：不配 `engine.warmpool` → 引擎零任务、零流量、`/v1/tasks` 零池行
  （S6 验证 2.5s 内 tasks_total 恒 0）。

## 4. 冒烟踩坑备忘

1. **Adapter.stop() 原来只置标志**——`ws.recv()` 阻塞使 WS 连接不关、节点
   端 agent 仍在线 → S5 前两轮失败。给 `TaskAdapter` 补了硬关连接（stop()
   即 `ws.close()`，节点立刻 client_offline）。这对 SDK 是实质修复。
2. **`find_agent_node` 对本机注册不滤 online**——warmpool 的在线闸必须用
   新增的 `agent_online`；原始依赖 find_agent_node 的实现会让离线成员持续
   被预热（S5 抓到的真 bug）。
3. warmpool 视图断言别写 `(a or {}).get("x") or {}` 链——优先级歧义，统一
   先 bind 再取。

## 5. 验收门关联与残留

- 「冷启动 <200ms」的路径分解：**引擎派发上界 = tick 200ms**（到点即派），
  **承接延迟 = 常驻桥收帧即回**（无冷启动，warm_runs 即证）。多机真实时延
  需验收门（20 机 200 任务）实测。
- 残留（v0.7 评估）：① 预热任务的终态行长期留存于任务表（面板可见 warmpool
  correlation 行），可考虑按期归档；② 真任务对热位 prefer 的亲和调度（当前
  bin-pack 只按额度，不感知"热"）；③ 成员自动发现（当前显式名单）。
