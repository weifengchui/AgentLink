# v0.6 P1 GitOps 目录驱动 — 实现与验证（2026-10-19）

对应路线图 v0.6：「**GitOps：watch 仓库 tasks/ 目录自动 apply**【设计案 §8.3】」——
把声明式任务提交纳入**仓库即真相源**的工作流：编排方在仓库里写/改/审 task_spec，
节点轮询目录自动进引擎表。

---

## 1. 语义

- **缺省关闭**（`gitops.enabled=false`，段可整体缺省）：完全惰性、零副作用。
- **开启后**：每 `interval_secs`（默认 15s）扫描 `gitops.dir`（仓库内 `tasks/`
  目录；根层 + 一层子目录的 `*.json`，排序后按名稳定处理）：
  - 新文件 / 内容 sha256 变化 → `reconcile::apply_task_spec` 入引擎表
    （与 `POST /v1/tasks` **同一内核口径**：必填门 / 非终态 409 / journal / 快照）；
  - 同内容不再重 apply（指纹观察；`mtime` 抖动/重写无害）；
  - 解析失败 → 告警一次并记观察（同一坏内容不蝉联告警；作者改好内容后指纹
    变化自然重报）；journal 失败 → 告警、保留观察下一拍重试；
  - 文件删除 → 清除观察项（**不删除任务**：生命周期由 DAG/取消、API/CLI 管）。
- **mesh 依赖**：gitops 是引擎的声明式入口，必须 `mesh.enabled=true`（license
  有效）才有去处；mesh 缺席时启动打 error 并**不 spawn**（空态不崩）。
- **重启语义**：扫描状态纯内存，重启后全量重扫——未清扫重投 = 幂等 409，
  终态 = 粘性读回，无重复行（声明式的最终态收敛，不依赖状态文件）。
- **轮询而非 notify**：单二进制形态下不引入 fs-watch 依赖；`interval_secs`
  2~15s 即可近似实时（git 提交/Push 场景天然低频）。

## 2. 内核口径共享（重构：`reconcile::apply_task_spec`）

`POST /v1/tasks`（api.rs）的内核部分抽成 `reconcile::apply_task_spec(mesh, body)`
+ `reconcile::ApplyFail` 分类（NotObject/MissingTaskId/MissingType/Conflicting/
DuplicateSeq/InvalidSpec/Journal/SerializeRow）+ `reconcile::rollback_row`。
HTTP 层映射为既有 400/409/202/500（响应字符串逐字节不变——engine_store 冒烟
p2-dup-409、p4-delete-nonterminal-409、p3-dup-409-after-reboot 全绿确认）；
GitOps 层映射为日志（409→debug"already present"、解析失败→warn"kept unapplied"）。

## 3. 配置

```json
"gitops": {
  "enabled": true,
  "dir": "/srv/agentmesh-repo/tasks",   // 仓库内任务目录
  "interval_secs": 15                    // 内容 sha256 差分轮询
}
```

## 8. 边界与后续

- 深层子目录与 `.yaml`/`.toml` spec 形态暂不支持（协议 §2 是 JSON）。
- 文件删除不回撤任务（设计如此）；「删除即取消」可后续加 `gitops.on_delete`
  策略位（缺省 keep）。
- 仓库侧建议：spec 文件带 `task_id` 版本化命名（`<name>.json`），不可变内容；
  真要"改"就写新 task_id——与本内核的首见定版/409 语义天然契合。
