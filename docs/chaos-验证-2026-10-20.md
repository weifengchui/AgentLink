# chaos 第一波验证：kill-node ×3 自动回收任务（2026-10-20，v0.7）

路线图 v0.7 的验收门之一是「chaos 注入 kill-node×3 自动回收任务」。本波交付
**kill-node 最小闭环**：引擎能识别「任务所在节点已失联」，在独立宽限期后把
任务退回待调度队列换机重派，并对重派次数做独立预算；同时修掉两个在慢执行
器下才暴露的调度口径问题（负载少算、死节点仍可派发）。

latency / disk-fill 注入与 kill-node 的 20 机实机版留待后续。

## 1. 拓扑与配置

```
S(seed, engine) ── W1 W2 W3 W4 W5（直接星型，慢执行器 12s）
                       ↑ 依次 kill W1/W2/W3（每个都持有在飞任务）
```

```jsonc
"mesh": {
  "enabled": true,
  "engine": {
    "max_retries": 8,          // 既有执行方失败重试预算（与本波无关）
    "backoff_secs": 0,
    "tick_ms": 200,
    "max_concurrent_per_node": 1,
    "reclaim": { "enabled": true, "grace_seconds": 3, "max_attempts": 3 }
  }
}
```

缺省 `reclaim.enabled=false` = 既有行为**逐字节不变**（不新增任何调度过滤）。

## 2. 语义

| 场景 | 行为 |
|---|---|
| 节点在线判定 `Router::node_online` | 本机恒在线；直连 peer 表在线；中继目录新鲜 → 在线；**最近断开过的直连节点**（5 分钟记忆）→ 明确离线；其余未知节点按在线处理（保持既有调度语义） |
| 派发过滤 | fleet 缓存里的 agent 可能比节点存活更久（`agents_update` 不随断链失效）——派发候选按 `node_online` 过滤，死节点不再接新活 |
| 负载记账 | 「已派发但尚未被 accepted」的 Pending 任务也计入节点并发额度（此前只算 Running，慢执行器下会被重复派发、压过 `max_concurrent_per_node`） |
| 失联回收 | 只回收**在途**任务（Running，或已派发未 accepted 的 Pending）且目标节点明确离线；宽限期到点 → `attempts+1`；未超预算 → 清空 `to_agent`/`assignee_node` 回 pending 换机重派；超预算 → failed 终态 |
| 预算 | `reclaim.max_attempts`（缺省 3）独立于 `max_retries`——节点死亡不是执行方业务失败，不占执行方重试预算 |
| 状态权威 | 引擎不伪造 `task_result`、不直接置 succeeded；只做「失联超时」判定与重派，终态仍由执行方回执推进 |
| 任务绑定 | `TaskRecord.assignee_node`（加性、缺省不存在）记录派发目标节点，节点死亡后即使 fleet 缓存被清也能判定归属 |

## 3. 改动面

- `src/config.rs`：`EngineConfig.reclaim` + `ReclaimConfig{enabled,grace_seconds,max_attempts}`
  （均 serde default）。
- `src/taskengine.rs`：`TaskRecord.assignee_node`（`skip_serializing_if`，旧行字节不变）。
- `src/router.rs`：`node_online` / `mark_node_offline` / `offline_nodes`（重连清除、
  直连断开记录）；`register_peer`/`unregister_peer` 接线。
- `src/reconcile.rs`：
  - `reclaim_offline_tasks`（maintenance 每拍执行；`reclaim_since` 记录首次观测离线时刻）；
  - 派发候选按节点在线过滤；负载记账纳入「已派发未 accepted」；
  - `mark_assigned` 写 `assignee_node`。
- 单测 +2：`reclaim_requeues_offline_node_task_after_grace`（宽限期、重派、
  预算耗尽终态）、`node_online_semantics_local_unknown_offline_dir`。

## 4. 验证

### 冒烟（6/6，`tests/chaos_smoke.py`，端口 18934-18939）

| 场景 | 结论 |
|---|---|
| K0 组网：S 见 5 个在线 peer + 5 个在线 agent | PASS |
| K1 6 个 12s 慢任务分散到 5 个 worker（每节点并发 1） | PASS |
| K2 依次 kill W1/W2/W3，每个被 kill 时都持有在飞任务 | PASS |
| K3/K4 kill-node×3 后 6/6 succeeded、pending/running 均 0 | PASS |
| K5 回收证据：被 kill 节点的任务在幸存节点重跑（attempts≥1）+ 引擎日志 3 条 `chaos reclaim` | PASS |
| K6 幸存节点无崩溃 / 被 kill 进程已退出 | PASS |

证据（`tests/chaos_smoke.jsonl`）：`chaos-00` 先被 W1 kill、重派到 W3 后再次
被 kill，最终在 W4 成功（attempts=2）；`chaos-01` 从 W2 重派到 W5；3 条
reclaim 日志对应 3 次 kill。

## 5. 边界与残留（chaos 后续波次）

1. **latency / disk-fill 注入未交付**：本波只做 kill-node；延迟/磁盘故障需要
   `tc`/`fallocate` 等外部工具与 root 权限，留待独立脚本。
2. **叶子经中继的回收**：`node_online` 依赖直连断开记忆；经 spine 学到的叶子
   在目录 TTL 过期后回到「未知按在线」，不会触发回收（任务可能永挂）。
   第三波应在中继侧做回收，或在目录过期时显式标记离线（需防脊柱抖动误杀）。
3. **at-least-once**：被杀节点若在死亡前已产生副作用但回执未送达，重派会
   二次执行——与既有投递语义一致，执行方需按业务键幂等。
4. **宽限期下限 1s**：极短 grace 可能早于心跳/目录收敛，造成误回收；缺省 10s
   大于默认 `heartbeat 3s + offline_timeout 6s`。
5. **真 20 机 LAN 的 kill-node×3** 仍待实机（本波为单机多进程仿真）。
