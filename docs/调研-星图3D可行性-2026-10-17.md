# 星图大屏『3D 展现形式』可行性调研报告

日期：2026-10-17 ｜ 范围：仅调研评估，不含实现 ｜ 对象：`web/starmap.html`（消息星图，现 2D canvas 手绘、零依赖单文件，约 70KB）

## TL;DR（结论先行）

**条件推荐**：不建议用 3D 替换现有 2D 星图（文献压倒性表明：对平面同嵌图这类"无天然第三维"的数据，3D 通常降低可读性与导航效率）；但**建议用 2～5 人日做一次一次性 3D 原型**——技术上完全可行：`3d-force-graph` 提供单文件 UMD（实测 1.39MB，可 `include_str!` 进二进制、离线可用、零构建链），性能对 ≤100 节点 / ≤500 连线有巨大余量（余量约三个数量级）。是否转正为产品功能（2D/3D 双模式），由原型的可读性实测决定。优先级上，**改良 2D（话题过滤、边捆绑、focus+context、小地图）的收益/成本比高于 3D**。

文中"实测"= 本报告写作时（2026-10-17）由 jsDelivr/npm 元数据 API 与 unpkg 下载 + `gzip -9` 得到的数字；"推断"= 我的分析判断，未直接引自文献。

## 1. 3D 图可视化的正反证据综述

### 1.1 反对 3D 的证据（主流结论）

- **深度是低级视觉通道**。Munzner《Visualization Analysis and Design》(2014) 第 5 章的通道排序中，"Depth (3D position)"位于位置/长度/角度等平面通道之后；第 6 章经验法则明确列有 **"No unjustified 3D"**（无正当 3D 结构就不要用 3D）。讲义原文可查：
  - https://www.cs.ubc.ca/~tmm/courses/547-17/slides/marks.pdf （Ch5 Marks & Channels）
  - https://www.cs.ubc.ca/~tmm/courses/547-15/slides/rules-artery.pdf （Ch6 Rules of Thumb，"No unjustified 3D"）
  我们的星图数据（节点→agent→话题泳道）是为屏幕平面**人工嵌入**的，第三维没有数据语义——正好命中该法则的禁止情形。
- **3D 自由度增加导致性能与整洁度下降**。Cockburn & McKenzie（CHI 2002）实验：允许用户在第三维自由摆放物品后，无论物理模型还是虚拟系统，**检索性能随维度增加而劣化**，主观感受"更 cluttered、更低效"；其 2001 年 Data Mountain 的 2D vs 3D 对照无显著性能差异（仅主观偏好 3D）。同一综述段落还引 Wickens et al. 1995：3D 显示改善横向导航但**显著损害垂直轴性能**；引 Risden, Czerwinski, **Munzner**, Cook：web 内容 2D vs 3D 可视化在性能与满意度上**无显著差异**。
  - https://www.csse.canterbury.ac.nz/andrew.cockburn/papers/chi02DM.pdf
  - https://www.csse.canterbury.ac.nz/andrew.cockburn/papers/ijhcs2D3D.pdf
- **动画/运动收益有限**。Tversky, Morrison & Bétrancourt 2002《Animation: Can it facilitate?》（IJHCS 57:247-262）综述近 100 项研究：**没有一项研究显示动画优于丰富的静态图示**——对"3D 旋转/飞行动画展示消息流"这类卖点应保持高度警惕（3D 大屏很容易犯"为动感而动感"）。
  - https://serc.carleton.edu/resources/871.html （作者预印本入口）
  - https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/bv_ch19.pdf （Microsoft Research 章节，转述同一结论）
- **遮挡与导航成本**（推断+上述文献综合）：透视投影下远端节点被近端遮挡、连线在深度上纠缠不可分辨；引入 orbit/fly 相机后，用户要先学会"转动才能看清关系"，而上述 Cockburn/Wickens 实验表明这种学习通常换来的是任务性能下降而非提升。

### 1.2 支持 3D 的证据（3D 占优的场景）

- **数据有天然 3D/几何结构时**。Munzner 斯坦福博士论文《Interactive Visualization of Large Graphs and Networks》(2000)：H3 用 3D 双曲几何做 focus+context 超链接浏览、扩展到 10 万+节点；Planet Multicast 用"地球上的真实 3D 弧线"帮助维护者发现误配隧道——**"literal 3D"（布局维度=数据真实维度）时 3D 有效**。
  - http://graphics.stanford.edu/papers/munzner_thesis/
  推论：若将来 AgentLink 引入机房/机柜/可用区之类的**物理拓扑维度**，或做跨云地域的地理布局，3D 才有数据语义支撑。
- **特定感知原语在 3D 上成立**。Healey《Perception in Visualization》汇总：3D 深度线索与 3D 朝向可做前注意处理（Enns & Rensink 1990 的"3D 朝向 pop-out"、Nakayama & Silverman 1986 的立体平面分组——**立体深度平面上可逐层并行搜索，干扰不跨层**）。但注意：这些红利主要依赖**立体（stereo）或强运动视差**，单目平面屏幕上的透视深度线索弱得多（同页也指出深度属于较弱通道，且 Cockburn 2002 明确提到屏幕无法复现焦点深度等线索）。
  - https://www.csc2.ncsu.edu/faculty/healey/PP/
- **时序/流动表达**（推断）：消息粒子沿弧飞行这类"流"的信息，3D 里可以用高度或深度做额外一维编码（如把话题热度映射 z 轴）；但文献未证明这种"人工第三维"优于用大小/颜色/时间切片编码。

**小结**：文献共识是——3D 的适用条件是"数据本来就有第三维"或"提供立体/运动视差线索"；纯平面嵌入图 + 单目屏幕 + 大屏观赏用途，正是 3D 最不划算的组合。用户"觉得立体会好很多"的直觉，与 Cockburn 的"主观偏好 3D 但客观性能更差"实验结果高度吻合。

## 3. 交互迁移成本盘点（现有 2D 功能 → 3D 对应物）

现有功能已在 `starmap.html` 源码核实：悬停话题卡组（`.gcard` DOM 卡片锚在光标，L102-132/463-527）、主从消息弹窗、胶囊拖拽（L299）、话题聚焦过滤（L404"ONLY the relevant topic lanes"）、实时滑窗+滑杆（L196）、canvas 截图（`toDataURL` L834）、30fps `captureStream + MediaRecorder` 录屏（L821）。

- **悬停卡组/弹窗**：3D 下 DOM 覆盖层依然可行，两条标准路：① three.js `CSS2DRenderer`（实测在 npm 包内，仅 8KB）把 HTML 元素按 3D 锚点同步投影到屏幕；② 每帧对目标 `Vector3.project(camera)` 换算屏幕坐标自持定位（推断：业界通用做法，即"屏幕空间投影锚定"）。**结论：可行，成本中等**；难点不是锚定而是遮挡语义——被挡住的节点该不该显示卡片、如何提示（推断，这是 3D 新增的设计债）。
- **拾取/命中**：three.js `Raycaster` 逐帧或 hover 时对胶囊球体求交（100~400 个球体射线测试开销可忽略——推断）。
- **拖拽避让**：3d-force-graph 官方示例即有"Fix nodes after dragging""Click to focus on node""Fit graph to canvas"（README 示例清单核实），拖拽=在相机平面上反投影，比 2D 略糙（深度不确定，需锁 z——推断）。现有 2D 的"等角分布双胶囊"布局逻辑需重写为力导向参数，属放弃而非迁移。
- **相机控制学习成本**：新增 orbit/fly 两套手势，与现有 hover/拖拽/点击存在手势冲突（如滚轮缩放 vs 滑窗滚动），iframe 嵌入总览时尤甚（推断；3d-force-graph 内置 OrbitControls/FlyControls 示例，实现成本低，但**交互设计成本不低**）。
- **文本标签可读性**：3D 里文字必须永远朝向相机（billboard sprite / three-spritetext，9KB）或 HTML overlay；旋转场景中密集标签重叠遮挡比 2D 严重，需要标签分级显示/聚簇——3d-force-graph 的"Text as nodes / HTML in nodes"示例证明能力存在，"1920×1080 大屏 400 个胶囊都有短名"的清晰度是原型必须回答的问题（推断，也是最大的可读性风险点）。
- **截图/录屏**：WebGL canvas 同样支持 `toDataURL`（需 `preserveDrawingBuffer:true`）与 `captureStream`+`MediaRecorder`（推断：与 2D canvas 同一套 API，迁移成本低）。
- **数据层不变**：REST/WS 轮询、配色、滑窗逻辑与渲染层解耦，两模式共享（推断，现有代码结构支持与否需在原型期确认）。

## 4. 100 节点级性能评估

- **余量**：目标规模 ≤100 节点 / 200-400 胶囊 / ≤500 弧线。参照系：3d-force-graph 官方示例直接演示 **~4,000 元素**图（README"Large graph (~4k elements)"核实）；cosmos.gl README 主张**数十万点/线**实时模拟；Sigma/mobius 类 WebGL 图库普遍面向千级到十万级。**结论（推断，基于以上参照）：我们的规模比这些库的设计点低 1～2 个数量级，几何/连线/粒子渲染完全不构成瓶颈——3D 不比 2D 慢，甚至比现有手绘全重绘 2D 更省。**
- **真瓶颈（推断，文献支撑如 §1.2 Healey 页）**：① 文字标签的注意力读取与屏幕空间重叠；② 遮挡——深度上重叠的弧线和被前层节点挡住的后层实体；③ 交互命中在旋转态下的不稳定；④ 力导向布局收敛抖动（大屏上"总在动"反而降低可读性，需 `pauseAnimation`/低 alphaDecay）。性能优化的正确对象是标签数与每帧 DOM 覆盖层，而非 draw call。
- **最低硬件**：WebGL 需要 GPU 环境；Chromium 已**废弃 SwiftShader 自动软件兜底**，"WebGL context 创建可能直接失败，站点应自行 fallback 到 Canvas2D 或提示"——官方文档：https://chromium.googlesource.com/chromium/src/+/HEAD/docs/gpu/swiftshader.md 。**含义：3D 模式必须保留 2D 兜底检测（`canvas.getContext('webgl2')` 探测），无独显核显/老集显跑 100 节点级 WebGL 无压力（推断），但禁用 GPU 加速的企业策略会直接掐掉 3D——商用可售阶段这是硬性需求。**

## 5. 中间路线与诚实对比

| 路线 | 收益 | 代价 | 依据 |
|---|---|---|---|
| **A. 改良 2D**（话题过滤/泳道淡出、边捆绑、分层环带、小地图、鱼镜 focus+context） | 直击"复杂交错容易乱"的痛点主体：交错=连线密集，**bundling 与过滤是文献中处理密集连线的正解**（Holten 2006 TVCG 12(5)：bundling 显著降 clutter：https://cs.jhu.edu/~misha/ReadingSeminar/Papers/Holten06.pdf ；H3 的 focus+context 思想可在 2D 用放大/降透明实现：Munzner 论文） | 现有渲染循环内增量改，无新依赖 | 诚实提醒：Lee et al. CHI 2012 实验（https://dl.acm.org/doi/10.1145/2254556.2254670 ）发现 bundling 降乱但**不必然提升理解**，需按话题聚合设计（我们的"话题泳道"天然适合按话题捆绑） |
| **B. 2.5D**（倾斜透视的 2D：z 只作热度/时间编码+深度线索） | 视觉"立起来"、大屏氛围好；数据仍 2D 语义，遮挡可控 | 投影/拾取/标签锚定要自建；文献上等价于"给深度通道一个弱编码"，Munzner 排序里深度恰是弱通道 | §1.1：收益主要是审美而非分析效率——要明说不骗自己 |
| **C. 真 3D（3d-force-graph）** | 探索性视角、演示冲击、未来接物理拓扑数据（§1.2） | 交互迁移 + 标签遮挡 + 相机学习成本 + exe +1.4MB | 上述全部证据 |

三者都保留 Canvas2D 兜底路径不冲突（SwiftShader 文档要求如此）。

## 6. 分期建议（工作量为推断，按 1 人熟悉 vanilla JS + 现有代码库计）

**阶段 0（立即做，优先于任何 3D）——改良 2D**：话题级过滤开关与按话题边捆绑、hover 聚焦淡出（L404 已有雏形可泛化）、小地图。约 **2–4 人日**。风险低；即使将来上 3D，这些改进同时受益。
**阶段 1——一次性 3D 原型（值得投，预算封顶 3 人日）**：vendored `3d-force-graph.min.js` + 一个临时 html，从现有 `/v1/history/search`/`/v1/peers` 拉真实规模数据，只验证三件事：① 100 节点/400 胶囊/500 线默认视角+自由旋转下的标签可读性；② 悬停卡组投影锚定的手感；③ 力导向布局在大屏上的"安静度"。验收门槛（推断）：默认视角下不旋转即可讲清一个话题链；达不到即停。**不改现有 starmap.html、不进产品路径。** 风险：结论不可迁移（真做时要重做交互层）——控制在 3 人日内即不亏。
**阶段 2（仅当阶段 1 过门槛；个人→OPC 阶段也可不做）——双模式产品化**：WebGL 探测+2D 兜底、CSS2DRenderer 迁移卡组/弹窗、相机预设（固定 3–4 个机位+一键回正而非放任自由旋转，对冲 Cockburn 的导航成本）、截图录屏迁移、iframe 手势冲突处理、配色/图例联动。约 **8–15 人日**。风险：交互打磨远超渲染工作量；exe +1.4MB 需用户确认接受。
**阶段 3（商用可售才考虑）**：Cosmos 路线仅在客群真出现 ≥1k 节点/≥10k 边（如多租户汇聚）时立项，否则不预付该复杂度。

按产品阶梯映射：**个人自用/OPC**：阶段 0 即够，3D 属玩具税；**中小团队**：阶段 0+1，3D 大屏在"汇报演示"场景有情绪价值但按原型门槛说话；**商用可售**：阶段 2 完成"条件推荐"的全部前置（兜底、相机预设、可读性验证）。

## 7. Verdict（一段话）

**条件推荐。** 文献（Munzner 的"No unjustified 3D"与深度弱通道排序、Cockburn 2001/2002 的 3D 自由度增加反而劣化任务性能、Tversky 2002 的动画收益证伪）一致反对把 3D 当**分析界面**用——星图数据没有天然第三维，用户"立体会更好"的直觉属于已被实验反复证伪的主观偏好；但作为**大屏观赏/演示模式**，3D 的工程门槛从未如此低：3d-force-graph 单文件 UMD 实测 1.39MB 可直接 `include_str!` 进二进制、零构建链、离线可用，100 节点/500 线对 WebGL 是三个数量级的降维打击，真瓶颈只在标签、遮挡与相机交互。因此：先花 2–4 人日做改良 2D（话题过滤/边捆绑/聚焦淡出，这才是治"乱"的药），再花不超过 3 人日跑一个一次性 3D 原型验证默认视角可读性，通过门槛才投 8–15 人日做 2D/3D 双模式产品化，且产品化必须包含 WebGL 失败自动回退 Canvas2D（Chromium 已废弃软件渲染兜底）与"固定机位优先"的相机策略；任何情况下不要用 3D 替换现有 2D。
