# 任务引擎内核化 · 设计（v0.6 首项，2026-10-18）

对应路线图 §2「任务引擎内核化：声明式 CRUD + reconcile loop + bin-packing 调度」与 §7 商业模式（v0.6 = AgentMesh 收费起点）。协议正本：docs/task-protocol.md（不动，协议先行内核后置）。

约束核对：单二进制零依赖、agentlink.json 全程向后兼容、老节点混跑不破、fleet 现全 0.5.9（4 台 Windows）。

## 0. 拍板记录（用户 2026-10-18 13:35，四项全过）

1. **发版载体**：M1（休眠骨架）走 **0.5.10** 预演 taskstore 持久化，小步上 4 机 fleet 滚动；M2+ 起进 0.6.0。
2. **收费边界**：**写面+引擎循环+调度整体=AgentMesh**；免费层只留发帧/history 投影/`apply` 薄壳。durable-submit 不下放免费。
3. **license 粒度**：**按节点数 tier：Starter≤15 / Pro≤50**（与按节点计费口径一致）；license.toml 内 node_quota 由 tier 决定。
4. **引擎默认语义**：`max_retries` 缺省 **0**（显式声明才重试）、backoff **固定 30s 可配**；**drift/declined 只告警不自动换机重派**（守执行方唯一状态权威）。

其余开放问题主会话定案：验签用纯 Rust `ed25519-compact`（编译期依赖，运行时零外部依赖不破单二进制）；`task_expired` 先仅引擎表+告警不动协议；业务级 `task_ack` 引擎推迟 v0.7；单机自动拉起 executor 预热推迟。

### 1.2 桥层已有（scripts/task-proto，上提语义的参照物）

- `tasklib.py`：`Bus.events()` 增量观测（409 环旋转→history 全量重建，`:60-77`）；`features()` 旧节点静默回退；`make_spec/msg` 协议 §2 构造器；`blob()` 脱敏面匹配坑注释。
- `taskctl.py`：编排收敛参考——`wait()` 事件驱动 + `expired` 超时判定 + `drift_after = 3×interval_s` 心跳缺勤判定（`:38,91`）；`submit()` 金丝雀闸口 `CANARY_BLOCK`（correlation 首任务未 succeeded 阻断后续，`:97-110`）。
- `executor.py`：执行方契约参考——`requires` 能力门→`task_declined`（`:31-33`）、sha 预检→declined、`accepted→progress×stages→succeeded` 全链、`maintain` 周期心跳（`:46-56`）、`task_cancel`→`cancelled`、`(task_id,seq)` 业务级幂等 `SEEN`（`:96-100`）、`upgrade_notice` 旧 topic 兼容双发。

### 1.3 缺口（本设计要补的）

1. **无任务持久存储**：`/v1/tasks` 是 history 环投影——环有界（`config.rs:140 history_len`）、重启即空、字段已脱敏（`spec` 非原文）。引擎需要原文 task 表。
2. **无任务写面**：REST 无 POST/PUT/DELETE `/v1/tasks`；`apply` 只是发帧，内核不知道"期望态"存在。
3. **无引擎循环**：expired/drift/retry/金丝雀判定全在桥层 Python 轮询里；内核无期望态-实际态收敛动作。
4. **无调度**：无 candidate 筛选（requires × capabilities × tags × online × 并发额度）、无 bin-packing、无协议 §5.5 并发上限实现。
5. **无断点续传**：内核重启后 in-flight 任务只能靠编排方从投影重建；引擎自身状态不持久。
6. **无 license/feature gate 设施**：features 静态数组；无 license 文件校验路径。

## 2. 内核设计

### 2.1 任务持久存储（`src/taskstore.rs` 新文件，复用 store.rs 模式）

`data_dir/tasks/` 子目录，两件套：

- `tasks/journal.jsonl`：append-only，行形状对齐 `store::Rec`——`{op:"up"|"del", task_id, rev, rec?}`，`rec` 为整行 TaskRecord JSON（非消息级，任务级粒度即可，≤100 机 × 并发百级体量小）。写入走 `Journal.record` 同款 fsync；启动 `replay()` 容忍断线尾行。
- `tasks/state.json`：`write_json_atomic` 全量快照（终端任务按留存策略清扫后落盘，journal 随之 `compact`）。

`TaskRecord` 字段（内核态，非协议态）：

```
task_id, spec(Value 原文，未脱敏——本机 data_dir，重启续传要原文),
state(pending|running|cancelling|terminal*), assignee{node_id,agent_id}?,
attempts, next_retry_at?, last_event_seq(观测水位), created_ts, updated_ts,
correlation, priority, terminal, blocked_count?, engine_note?
```

trail 不落 task 表——轨迹真相仍是 history 环（单一事实源原则不动，`router.rs:2197 tasks_view` 注释）。投影与表不一致时：表赢（state/assignee 以引擎为准），trail 以 history 为准；重启对齐：快照+journal → 对 history 环回放补投引擎缺席期间看到的事件；环旋转够不着的 running 行退化为按 deadline/drift 规则判。

### 2.2 REST 面（命名对齐 `src/api.rs:137-178` 现有风格）

| 路由 | 语义 | 层 |
|---|---|---|
| `GET /v1/tasks`（现有） | 列表。引擎启用且 license 有效时，返回体升级为表驱动 TaskView（字段是现有 TaskView 的**超集**：新增 `source:"engine"`、`attempts`、`assignee`、`next_retry_at`；老消费方零破坏），`?source=history` 可强制旧投影 | 投影免费，表驱动视图 Mesh |
| `POST /v1/tasks` | 声明式创建：body=task_spec（协议 §2 原文）。校验+落表（pending）即 202 `{task_id}`；派发由引擎做。幂等：同 task_id 重复 POST 且未清扫 → 409 | Mesh |
| `GET /v1/tasks/{task_id}` | 单任务详情（表+trail 合并视图） | Mesh（表存在时）；license 无效时回退 history 投影语义 |
| `POST /v1/tasks/{task_id}/cancel` | 写侧发 `task_cancel` 帧 + 表置 cancelling | Mesh |
| `DELETE /v1/tasks/{task_id}` | 仅终态可清扫（journal del） | Mesh |

鉴权沿用 local API token（`api.rs authorized()`）；license 门失败统一 `403 {"ok":false,"error":"mesh_license_required"}`。`/v1/health` 的 `features` 改为动态数组：mesh 生效时追加 `"engine"`。

### 2.3 任务状态机（协议 topic → 引擎动作）

复用 `tasks_projection` 已验证的迁移语义（`router.rs:745` 与单测 `:428`），抽为纯函数 `TaskRecord::apply_event(topic, payload)`，放 `src/taskengine.rs`：

| 事件 | 非终态迁移 | 引擎动作 |
|---|---|---|
| `task_accepted` | pending→running（置 assignee 回执）/ failed 后重派再 accepted→running | 清 next_retry_at |
| `task_declined` | pending→declined [终]（执行方唯一状态权威，协议 §3） | 记录、告警，**不自动换机重派**（换机=重投 spec 新 seq，动作策略见开放问题 3） |
| `task_progress` | 不改 state，刷新 last_progress_ts/水位 | maintain 心跳喂 drift 判定 |
| `task_succeeded` | →succeeded [终] | 金丝雀放行（同 correlation） |
| `task_failed` | running→failed；attempts<budget.max_retries 且未 expired → pending(+backoff) | 重派入队 |
| `task_cancel`/`task_cancelled` | →cancelling/→cancelled [终] | 超时未确认按 drift 处理 |
| `task_rollback(_back)` | →rolled_back [终] | M3 护栏联动 |
| deadline 超期 | →expired [终]（编排方判定，协议 §3/§4） | 引擎写表+告警；是否外发协议消息见开放问题 7 |

`task_ack`（业务级确认）v0.5 桥层未做，引擎同样只依赖 topic 收敛——不阻塞本设计。

### 2.4 reconcile loop（期望态=task 表，实际态=总线事件流）

- **订阅**：进程内订阅 `Router.events: broadcast::Sender<Envelope>`（`router.rs:909`）——**不是** HTTP `/v1/events` 轮询（脱敏面，spec 非原文）；引擎在投递路径内看原文帧，按 `payload.task_id` 匹配表行，`(task_id,seq)` 幂等键去重（协议 §4，对齐 executor.py SEEN）。
- **tick**：独立 `tokio::spawn`（`main.rs:427 maintenance` 同款接线 + `:429 shutdown` 通道），周期 200ms（P99 调度延迟 <500ms 验收门的推论：入队→最迟派发一个 tick）。
- **每拍动作**（纯差值收敛，状态只由事件推进，内核不伪造执行方状态）：
  1. 消费事件流 → apply_event 落表（journal up）；
  2. pending 无 assignee → 派发（2.5）；
  3. deadline 判定 → expired；
  4. failed/retry：`next_retry_at` 到期 → 引擎以 `from_agent="engine"` 重发 `task_spec`（seq=attempts+1，executor 幂等不误拦）；
  5. maintain drift：`last_progress_ts` 缺勤 > 3×`reconcile.interval_s`（taskctl.py 语义上提）→ 动作默认值见开放问题 3；
  6. 快照/清扫到期终态行（留存时长配置）。
- **执行者侧契约零改动**：executor.py / hermes_bridge 照常收 spec 回事件——上提的是编排器，不是执行协议。老版本桥节点混跑无感。

### 2.5 bin-packing 调度（`src/scheduler.rs` 新文件，M3）

- **candidate**：`spec.requires` ⊆ `AgentRecord.capabilities`（`cap_matches` 逐条，全部满足）∧ `online` ∧ 所在节点 `tags` 不命中 `constraints.exclude_tags` ∧ 节点并发额度未满 ∧ 非 unschedulable（taint 标签 `!schedulable`，路线图 §4.5 接口预留）。agent 集 = 本机 `agents` ∪ 舰队 `fleet_agents`。
- **打分（≤100 机，贪心即可，不求最优）**：first-fit-decreasing——pending 按 `(priority 升序, created_ts 升序)` 排序（协议 §2：越小越优先），逐个装入 candidate 中**剩余并发额度最大、其次负载（在跑任务数）最小**的节点；同分按 node_id 字典序（确定性，测试可断言）。
- **并发额度**：每节点 `max_concurrent_per_node`（默认值开放问题 1）；全局 `max_inflight` 上限（协议 §5.5"限并发"落点）。
- **派发**=通过既有 Router send 路径发 `task_spec`（`to`+`to_agent` 定向，复用 offline 队列/pending-ack/重试 journal——帧级 0 丢失继承现网机制）。
- **单机舰队可用**：candidate 含本机 agent 时，派发即本机 inbox 路径，代码同一条——4 台 Windows 现网 fleet 直接可跑通全部验收用例。
- **金丝雀/批次护栏**（协议 §5.1/5.2）：correlation 维度状态挂表上（`first_canary_passed` per correlation），首任务非 succeeded 不放行同批 ≥50%；同批连续 2 个 failed/expired → 暂停整批置 `batch_paused`，等 `POST /v1/tasks/{id}/resume`（M3）。

### 2.6 超时 / 重试 / 断点续传语义

- **超时**：`spec.deadline`（ISO8601，可无）→ expired 终；无 deadline 的 one_shot 用引擎默认墙 `engine.task_default_timeout_seconds`（默认值开放问题 2）。
- **重试**：`budget.max_retries`（协议 §2 已有字段）；超限→failed 终。backoff 策略默认值开放问题 2。重试期间 assignee 清空重新进调度；换机重派与原地重派同为一次"重投 spec"，由调度器重新选 candidate。
- **断点续传**：内核重启→快照+journal 重放→history 对齐→引擎从 `next_retry_at`/drift 继续收敛；对执行方唯一要求是 `(task_id,seq)` 幂等（executor 参考实现已具备）。"任务体"续传（执行方内部从断点干）属执行方语义，内核只提供重投 seq 递增与 `task_progress.stage` 记录（trail 天然在 history）——真正 checkpoint 迁移压 v0.7（路线图 §3）。

## 3. license 边界与 gate 形态

### 3.1 分界（对齐路线图 §7 正本 + task-protocol.md §8）

| 免费（AgentLink OSS） | AgentMesh（收费） |
|---|---|
| 协议 spec 与全部消息语义（永久开源） | task 表持久存储 + 声明式写面（POST/DELETE `/v1/tasks`、`/v1/tasks/{id}` 表驱动详情） |
| `/v1/send` 任意发帧（含手发 task_spec） | reconcile loop（expired/drift/retry 自动收敛） |
| `GET /v1/tasks` history 投影（现有只读面） | bin-packing 调度、requires→assignee 匹配决策 |
| `cap_matches`/注册表/`/v1/events` 观测面 | 金丝雀、熔断、并发上限、批次暂停/放行 |
| CLI `apply` 单次薄壳提交（=发一帧，无引擎） | 断点续传重启重建、预热池/GitOps/webhook（v0.6 其余项，共用此 gate） |

红线自查：免费层传输完整、单独可用；bridge 层 taskctl.py 编排器在免费内核上照跑——我们不砍掉别人自研编排的路。

### 3.2 gate 代码形态（不破单二进制零依赖）

- **配置**：`agentlink.json` 新增顶层 `"mesh": { "enabled": false, "license_file": "license.toml", "engine": {…调参项} }`——`#[serde(default)]` 全程向后兼容（老文件缺段=免费层，`config.rs` 现行模式）。
- **license 文件**：`license.toml` = 明文段（customer/issued/expiry/node_quota/features）+ **Ed25519 签名段**；公钥内置二进制，私钥厂方持有；离线验签、绝不 phone-home（路线图 §7）。节点数校验：被 Mesh 调度的**不重复 node_id 数** ≤ node_quota，超出则调度拒绝新节点 + `/v1/health` 报 `"mesh":"quota_exceeded"`。
- **验签依赖**：现依赖表已有 sha2/hmac（`Cargo.toml:26-27`）但 HMAC 对称密钥藏不进可分发二进制（提取即伪造）。首选新增 `ed25519-compact`（纯 Rust、无 C 依赖、windows-gnu 交叉编译友好、no_std）——仍是单二进制零外部运行时依赖；备选见开放问题 4。
- **生效矩阵**：`mesh.enabled=false`（默认）→ 引擎不 spawn、写面 403、features 数组不变——**M1/M2 发布即滚动升级零行为变化**；`enabled=true` 且 license 无效→ 启动打 error 日志、退化为免费层运行（不 crash-loop，对齐 `read_json_opt` "空态好过崩"哲学）。
- **不做** cargo feature 双构建切分（v1.0 路线图 §4 再议仓库拆分）：0.6.x 期内核代码全在 OSS 构建里，靠 license 运行时门控——与"一个代码库、协议公开"一致。

## 5. 开放问题（需拍板）

1. **每节点默认并发上限** `max_concurrent_per_node`：常数（建议 2）还是按节点数公式？协议 §5.5 只写"默认按节点数"。
2. **重试默认值**：`budget.max_retries` 缺省 0（保守）还是 2？backoff 缺省：固定 30s vs 指数（30s→上限 10min）。无 deadline 任务的引擎默认墙时长。
3. **drift/declined 默认动作**：心跳缺勤只告警还是自动换机重派？`task_declined` 是否允许引擎自动重派到次优 candidate（倾向否——执行方唯一状态权威，declined 是终态）。
4. **license 验签依赖**：接受新增 `ed25519-compact` 纯 Rust crate（编译进单二进制，无运行时外部依赖），还是要求零新增依赖自写 RFC8032 验证？
5. **license 粒度**：tier（Starter≤15/Pro≤50 节点数）还是显式 feature 清单？`node_quota` 统计"被 Mesh 实际调度过的不重复 node_id"还是配置全集群节点数（离线场景后者算不准）。
6. **写面是否部分免费**：`POST /v1/tasks` 的"durable submit（落表不派发）"放免费层当 `apply` 升级版，还是整个写面起算 Mesh？
7. **expired 可见性**：只写引擎表+告警，还是新增总线消息 `task_expired` 让执行方也可见（协议加性改动，需 task-protocol.md 版本 bump）。
8. **task_ack**：引擎要不要实现业务级 ack 回执（桥层至今未做），推迟到 v0.7？
9. **发版节奏**：M1 直接进 0.6.0，还是先出 0.5.10 预演 taskstore 持久化上 fleet 滚动？
10. **单机舰队体验**：是否内置"自动拉起本机 executor 桥"（预热池 v0.6 项前移），还是 0.6 维持手动起 `executor.py`？
