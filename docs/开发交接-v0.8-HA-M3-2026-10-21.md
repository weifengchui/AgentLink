### 1.1 HA 现状能力（`ha.enabled=true` 时）

- 复制状态机 = **按命名空间分区的 KV**（`Put`/`Delete` 幂等）；
- 选举（pre-vote + leader 租约）、日志复制、提交推进（Raft §5.4.2 限制）；
- 日志压缩 + 快照：leader 主动给落后节点发 `InstallSnapshot`；
- 动态成员变更：joint consensus，一次只增删 1 个投票成员（Raft §6）；
- 读：默认本节点视图（最终一致），`/v1/ha/get` 传 `strong=true` 走
  **ReadIndex 强一致读**（leader 服务，follower 409，无 quorum 503）。

### 1.2 HA 尚未覆盖（别误以为已有 HA）

- **业务模块（taskstore / quota / audit / oidc 会话）仍各节点本地**——M4 才接线；
  现在 `ha.enabled=true` 只保证「KV 复制状态机」这一层的一致性。
- 新加入的成员必须**网络可达**（peer 通道靠 `discovery.static_peers` 建立）；
  `POST /v1/ha/members` 只改共识配置，不负责建连。
- 单节点 `ha.enabled=true` 也能跑（quorum=1），但无 HA 意义。

### 1.3 配置（`agentlink.json` 的 `ha` 段，全 serde-default）

```jsonc
"ha": {
  "enabled": false,                       // 缺省 false = 行为与 v0.7 逐字相同
  "cluster": ["ha-n1@127.0.0.1:19001"],   // node_id@host:port
  "voting_members": ["ha-n1", "ha-n2"],   // 缺省 = cluster 全部（奇数，≤9）
  "learners": ["ha-n4"],                  // 只复制不投票
  "election_timeout_ms": 1000,            // 300-5000，实际 1.0~1.5 倍抖动
  "heartbeat_interval_ms": 200,          // 50-1000
  "snapshot_threshold_entries": 10000,    // 1000-10000000
  "read_consistency": "leader",           // leader | local
  "fsync": "batch"                        // batch | always
}
```

### 1.4 API（`ha.enabled=false` 时全部 409 `ha is not enabled`）

| 端点 | 角色 | 说明 |
|---|---|---|
| `GET /v1/ha/status` | Operator+ | 角色/term/commit/applied/leader/quorum/`snapshot_index`/`voters`/`learners`/`pending_voters`/`joint` |
| `POST /v1/ha/propose` | Operator+ | 提交一条 KV 写；非 leader → 409 |
| `POST /v1/ha/get` | Operator+ | 读 KV；`{"strong":true}` 走 ReadIndex |
| `POST /v1/ha/members` | **Admin** | 动态成员变更，最多等 3s，返回 `committed`/`pending` |

## 4. 铁律（违反即返工）

1. **单二进制、零运行时依赖**：只允许纯 Rust 编译期依赖，**不允许 C 依赖**，
   不引入外部进程（redis/etcd 之类一律自己实现）。
2. **`agentlink.json` 全程向后兼容**：新段/新字段一律 `serde(default)`；
   `ha.enabled=false` 时行为与 v0.7 **逐字相同**。
3. **协议 `docs/task-protocol.md` 不动**；老节点混跑不破；响应新增键不删旧键。
4. **默认态钉死**：`ha.enabled=false` / `mesh.enabled=false` 时不 spawn 任何
   任务、不发任何帧、features 与上一版一致。
5. **中文文档 + 中文 commit 摘要**；每包 = 独立提交，测试断言进 `cargo test`，
   冒烟场景进 `tests/*.py`，每包跑全量门禁。
6. **不擅自 push**：新提交先本地留存，等主控/用户授权再推。
7. **不碰生产 8765**：冒烟一律用隔离端口段。

## 6. 避坑清单（M1~M3 真实踩过，勿重蹈）

1. **重启不重放日志 → 全员重启后状态机为空**：`restore()` 必须先落压缩基点，
   再重放 `base+1..applied`，并把 `applied_index` 持久化到 `state.json`。
2. **leader 收到 `AppendEntriesResp` 后无条件回发 → 与 follower 互刷成风暴**
   （实测单节点 3 百万条日志）：只在「对端还没追平」时补发下一批。
3. **`RequestVoteResp` 缺 `pre_vote` 标记 → 预选票永远无法转正**（选不出 leader）。
4. **`prev > 对端 last` 时 `conflict_index` 回 `prev` → `next_index` 原地打转**、
   永远追不上：要回「对端 `last+1`」。
5. **draining 判据不能只看 `match_index`**：commit 可能在该次追加之后才前移，
   对端此时还没学到新的 `leader_commit` → 被移出节点停在旧配置里反复选举、
   把 term 打高后抢走 leader。判据必须用 `AppendEntriesResp.commit_index`
   （对端处理完后的提交位点）。
6. **非成员候选者必须拿不到票**：否则已移除节点能靠旧配置重新当选。
7. **ReadIndex 少算 leader 自己这一票** → 3 节点挂 1 个 follower 后强读误报 503。
8. **压缩顺序**：先落快照成功 → 再压缩日志 → 再补持久化；快照写失败时**不压缩**。
9. **提交前还原未涉及套件的 `tests/*.jsonl`**（回归会改写它们）。
