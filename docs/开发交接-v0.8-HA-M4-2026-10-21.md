### 1.1 HA 现状能力（`ha.enabled=true` 时）

- 复制状态机 = 按命名空间分区的 KV：`task` / `quota` / `audit` / `oidc` /
  `cfg`（`src/ha.rs:32-36`，`NS_TASK`…`NS_CFG`）；`Put`/`Delete` 幂等。
- 选举（pre-vote + leader 租约）、日志复制、提交推进、日志压缩 + 快照、
  joint consensus 成员变更、ReadIndex 强一致读。
- **任务表**：leader 写 `task` 命名空间，follower 写面 409（带 `leader_id`）、
  无 leader 503；首次启用 HA 时 leader 把本地 journal 灌入状态机并写
  `cfg/task_seed_v1` 标记（`src/api.rs:447`），加入既有集群的节点以状态机为准。
- **配额**：60s 提交窗口复制在 `quota/rate/<ns>`；leader 内 `quota_ha_lock`
  串行读改写，新 leader 先 `await_caught_up` 再读窗口；活跃上限直接按复制
  任务表计数；观测面 `/v1/mesh/quota` 读复制窗口。
- **审计**：记录写 `audit/<seq20>`，seq/prev 在 leader 串行分配；任期变化后
  首次追加先从状态机重建链头并校验；`audit_event` 在 HA 下先落状态机，
  follower 把记录转给 leader。
- **OIDC**：`sess:<token>` 会话与一次性 `state` 均复制；`state` 用 leader
  原子 `take`（读旧值 + 删除同锁）保证跨节点只消费一次；30s 过期清理只在
  leader 侧跑。
- **单写者**：`taskengine` reconcile tick 与 `gitops` 目录扫描只在 leader 执行；
  follower 把任务帧转给 leader，并定时从状态机全量同步任务表。

### 1.2 HA 尚未覆盖（别误以为已有 HA）

- 只验证过 **3 节点本机 LAN**；跨机房延迟、分区下的读一致性、20 机规模归 M5。
- 业务写仍是同步 `propose_and_wait`：写延迟下界受心跳（默认 200ms）约束，
  实测单次提交 0.1~0.45s。
- 新加入成员必须**网络可达**（peer 通道靠 `discovery.static_peers`）；
  `POST /v1/ha/members` 只改共识配置，不负责建连。
- 审计是 best-effort：追加失败不阻断业务；链校验失败则停止追加并告警。
- learner 读仍有滞后（只复制不投票），强读必须打到 leader。


### 1.4 API（`ha.enabled=false` 时 HA 端点全部 409 `ha is not enabled`）

| 端点 | 角色 | 说明 |
|---|---|---|
| `GET /v1/ha/status` | Operator+ | 角色/term/commit/applied/leader/quorum/`snapshot_index`/`voters`/`learners`/`pending_voters`/`joint` |
| `POST /v1/ha/propose` | Operator+ | 提交一条 KV 写；非 leader → 409 |
| `POST /v1/ha/get` | Operator+ | 读 KV；`{"strong":true}` 走 ReadIndex，返回 `read_index` |
| `POST /v1/ha/members` | **Admin** | 动态成员变更，最多等 3s，返回 `committed`/`pending` |
| `GET /v1/mesh/quota` | Admin（或本租户 operator/viewer） | 返回 `namespaces`（**不是 `rows`**）、`scope`、`defaults`；HA 下 `submit_last_minute` 读复制窗口 |

M4 新增的内部链路（不是公开 API）：peer 控制帧 `ha_kv` / `ha_kv_resp`
（follower 把 KV 读写转发给 leader，`src/api.rs:178` `AppState::ha_kv`），
未知 action 老节点直接忽略 → 新旧混跑不破。

1. **单二进制、零运行时依赖**：只允许纯 Rust 编译期依赖，**不允许 C 依赖**，
   不引入外部进程（redis/etcd 之类一律自己实现）。
2. **`agentlink.json` 全程向后兼容**：新段/新字段一律 `serde(default)`；
   `ha.enabled=false` 时行为与 v0.7 **逐字相同**。
3. **协议 `docs/task-protocol.md` 不动**；老节点混跑不破；响应新增键不删旧键。
4. **默认态钉死**：`ha.enabled=false` / `mesh.enabled=false` 时不 spawn 任何
   任务、不发任何帧、features 与上一版一致。
5. **中文文档 + 中文 commit 摘要**；每包 = 独立提交，单测进 `cargo test`，
   冒烟场景进 `tests/*.py`，每包跑全量门禁。
6. **不擅自 push**：新提交先本地留存，等主控/用户授权再推。
7. **不碰生产 8765**：冒烟一律用隔离端口段。
8. **禁止用「放宽断言 / 调大超时 / 跳场景」制造通过**；失败先判性质
   （产品回归 / 环境冲突 / 测试自身），改断言必须能解释为什么原来的断言错了。

## 6. 避坑清单（M4 真实踩过，接续 M1~M3 那份）

1. **Raft 驱动不能挂在 tokio 定时器上**：worker 在 `block_in_place` 里等 apply
   时，tokio 的 timer 可能整体停摆数秒（实测 3.009s），心跳/选举超时随之停摆
   → 对端误判失联重新选主 → 在任 leader 的写请求 500/409 连锁。已改为专用
   OS 线程 `ha-ticker`；`try_send` 背压时只丢本帧（下一拍心跳重带状态）。
2. **锁序恒为 `inner` → `applied`**：`wait_applied` 的超时分支曾先持 `applied`
   再取 `inner`，与 `publish_applied` 相反，一旦在发布瞬间超时就永久互锁
   ticker 线程与等待者（现场表现为再没有任何超时日志）。超时必须先释放
   `applied`，由 `timeout_error_logged` 一次取 `inner` 完成错误分类与位点记录。
3. **`block_wait` 只在多线程 runtime 用 `block_in_place`**：`tokio::task::JoinSet`
   驱动的是 worker 线程，若不交接，整条 worker 都会被同步 apply 等待占住；
   `spawn_blocking` 线程里再 `block_in_place` 会 panic（回归用例
   `block_wait_yields_worker_driver`）。
4. **新 leader 必须先 `await_caught_up` 再改配额窗口**：否则会拿旧窗口写回去
   覆盖前任刚提交的计数（B3 换主后第 7 次必须 429 就是这条的验证）。
5. **加入既有集群的节点不要用本地旧 journal 覆盖状态机**：以状态机为准，
   首次迁移由 leader 灌数据并写 `cfg/task_seed_v1` 标记。
6. **`/v1/mesh/quota` 的字段是 `namespaces`**：测试辅助函数按 `rows` 取会拿到
   空视图（曾误判成 B3 产品缺陷）。
7. **冒烟串行、且别在构建后立刻连跑**：一次全矩阵连跑（刚 build 完、机器还
   忙）出现过 `quota_smoke` S4 与 `chaos_smoke` K2/K5 时序抖动失败——
   单独重跑同一二进制 7/7、6/6 全绿。判性质时先看是不是同机负载/时序，
   再去改产品代码；**不要为此放宽断言或加大超时**。
8. 沿用 M1~M3 那份的全部 9 条（重启重放日志、`AppendEntriesResp` 补发条件、
   `pre_vote` 标记、`conflict_index` 回退、draining 用 `commit_index`、非成员
   不投票、ReadIndex 算上 leader 自己、压缩顺序、还原未涉及套件的 jsonl）。
