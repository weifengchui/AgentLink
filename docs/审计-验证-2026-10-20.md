# 不可变审计日志 + 导出验证（2026-10-20，v0.7 §4.4）

路线图 v0.7：「不可变审计日志（hash 链 append-only）+ 导出 ELK/文件」。本包交付
**hash 链审计 + 校验/导出端点**：所有治理动作（任务写面、配置变更、降级开关、
控制面拒绝）逐条落 `<data_dir>/audit/audit.jsonl`，每条 `fsync`；链头随追加
前移，任何一行被改/删/插都能被 `GET /v1/audit/verify` 重新读盘发现。

缺省 `security.audit.enabled=false`：不建目录、不落盘、端点返回 `enabled=false`，
既有行为零变化。

## 1. 配置与端点

```jsonc
"security": { "audit": { "enabled": true } }
```

| 端点 | 角色 | 说明 |
|---|---|---|
| `GET /v1/audit/verify` | Admin | 重新读盘校验整条链：`{enabled, valid, count, head, error?}` |
| `GET /v1/audit/export?limit=N` | Admin | 最近 N 条（缺省 500，上限 5000）+ 清单 `{count, head, valid, error?, records}` |

`records` 为原始 JSON 行解析结果，可直接进 ELK/归档；`head` 是当前链头，
`count` 是有效前缀长度（损坏时报告最后一个有效记录）。

## 2. 记录格式与链

```jsonc
{"seq":1,"ts":1760000000,"event":"task.submit","actor":"admin",
 "node_id":"520000000001","detail":{"task_id":"aud-1","type":"audit.echo","state":"pending"},
 "prev":"","hash":"<sha256(prev ‖ '\n' ‖ canonical(body))>"}
```

- `body` = 除 `prev/hash` 外的字段；serde_json 的 Map 为 BTreeMap，键序确定，
  重放逐字节一致。
- `prev` = 上一条 `hash`，genesis 为空串；`hash` = `sha256(prev ‖ "\n" ‖ body)`。
- 每次追加 `write + sync_data`（审计量低，换取崩溃后尾部可界定）。
- 启动时校验整条链；损坏（含崩溃留下的半行）→ **fail-closed**：拒绝继续追加
  （error 日志），服务本身照常运行；修复文件并重启后恢复。
- 进程内被外部篡改：`verify` 立即发现；追加仍会按内存链头继续写（需要重启才
  fail-closed）——见残留 1。

## 3. 已接入的审计事件

| event | 触发点 | detail（不含密钥） |
|---|---|---|
| `task.submit` | `POST /v1/tasks` 成功 | task_id / type / state |
| `task.cancel` | `POST /v1/tasks/{id}/cancel` | task_id / state |
| `task.delete` | `DELETE /v1/tasks/{id}`（终态清扫） | task_id |
| `lockdown.set` | `POST /v1/lockdown` | on / blocked_out / blocked_in |
| `config.update` | `PUT /v1/config` 保存成功 | 仅变化的键名（`cluster_token` 只记键、不记值） |
| `handshake_rejected` | 握手版本/集群 token/准入拒绝 | reason / node_id / addr |
| `transit_rejected` | 中继验签失败 | msg_id / from |
| 其它 `audit_alert` | 路由层所有审计告警 | 原 payload（`kind` 作为 event） |

`Router::notify("audit_alert", …)` 统一入链（actor=`peer`），API 写面用实际角色
（admin/operator）。lockdown 的 `audit_alert` 由 API 显式写一条、路由钩子跳过，
避免同一次切换落两条。

## 6. 边界与残留（后续波次）

1. **进程内篡改的追加时点**：外部改文件后，`verify` 立即报 invalid；但运行中的
   追加仍按内存链头写（磁盘链已断），要等重启才 fail-closed。若需在线 fail-stop，
   可在追加前做「文件尾 hash/长度」轻量探测（O(1)）。
2. **导出仅尾部 N 条**：无 offset/时间范围/压缩包格式；ELK 需按 `records` 二次
   加工。后续可加 `from_seq`、gzip/文件包与 manifest 签名。
3. **无轮转/保留策略**：append-only 单文件，长期运行需外部归档；不做自动截断
   （截断会破坏链，必须走「归档 + 新链 genesis」显式流程）。
4. **actor 粒度**：控制面事件为 `peer`（detail 带自称 node_id，不作身份断言）；
   API 事件为角色名，未到具体 token/用户。ABAC/SSO 落地后再细化。
5. **存储层未加密**：依赖磁盘权限/全盘加密；WORM/对象锁留待部署层。
6. **业务终态不逐条审计**：task 状态流转由 taskstore journal 承担；审计聚焦
   「谁做了什么治理动作」，避免高频写放大。
7. **审计写失败不阻断业务**（可用性优先），但会 error 日志 + verify 可见；
   合规场景应配合 SLO/告警监控 `valid=false`。
