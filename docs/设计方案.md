# AgentLink 设计方案（v1.0 · 已定稿）

> 参考文档：《灵讯 AgentLink 最小版设计》
> 定位：局域网内多台机器上 Agent 之间的通信总线。只为程序服务，不为人聊天。
> 目标：**小、轻、稳、零配置**。一台机器跑一个常驻小进程（Node），Agent 通过本机接口收发消息/文件。
>
> **已确认的关键决策（2026-10-12）**：① 实现语言 = **Rust**；② 发现 = **UDP 广播为主，mDNS 可选**；③ 拓扑 = **Mesh 全互联 WebSocket**；其余按本方案默认执行。

---

## 0. 结论摘要（TL;DR）

- **实现语言：Rust**（已确认），编译为单文件可执行程序（Windows/Linux/macOS，release ~3–6 MB，无运行时依赖），最贴合"小而轻 + 多机部署"。
  - 未选：Go（开发更快但产物更大）、Bun/Node（开发最快但产物 50–90 MB）。
- **发现机制：UDP 广播为主，mDNS 为可选**（原文档两者并列；Windows 上 mDNS 依赖 Bonjour、Linux 依赖 avahi，不稳，因此把 UDP 广播作为默认主力，mDNS 作为补充，并支持静态 peer 列表兜底）。
- **拓扑：全互联（Mesh）WebSocket**，节点数少（<20）时最简、延迟最低；连接按 node_id 去重避免双连接。
- **可靠性：给原文档补上"送达确认"**。直发消息默认 at-least-once（ACK + 去重 + 有界重试 + 离线暂存 TTL），广播默认 fire-and-forget。原文档只写了"可靠送达"，但协议里没有 ACK/重试，这是最大缺口。
- **身份：node_id（稳定）+ name（可改）分离**。原文档用 `agent_name` 当地址，改名/重名会直接断链，需修正。
- **安全：局域网共享 token 握手 + 每帧 HMAC**，本地接口仅监听 127.0.0.1。不做公网、不做 NAT 穿透、不做端到端加密（留扩展位）。
- **协议加 `v` 版本字段**，为后续演进留路。

## 1. 对原始设计文档的评审

### 1.1 保留（方向正确）
- 只做通信层，不做任务板/角色/编排 —— 边界清晰，很好。
- 统一 JSON 消息信封（msg_id/from/to/type/action/payload/timestamp）。
- WebSocket 长连 + 心跳 + 离线检测。
- 文件传输的 `file_meta → accept → chunk×N → complete → done` 顺序流程。
- 本地 HTTP + WS 接口，供 Hermes / 其他 Agent 调用。
- 配置项设计（端口、广播端口、心跳、超时、token、最大文件）。

### 1.2 必须补齐（原文档缺口）
| # | 缺口 | 后果 | 本方案修正 |
|---|------|------|-----------|
| 1 | 无 ACK / 重试 / 去重 | 声称"可靠送达"但实际可能丢消息 | 引入 `ack` 帧、`msg_id` 去重、有界重试、离线暂存 |
| 2 | 用 `agent_name` 当地址 | 改名 / 重名即失联 | 引入稳定 `node_id`，name 仅展示 |
| 3 | 无协议版本号 | 升级后新旧节点无法共存 | 信封加 `v: 1` |
| 4 | 无鉴权 / 无防重放 | 局域网任意进程可冒充节点 | 共享 token 握手 + nonce + 帧签名 |
| 5 | broadcast 无防环 | 转发型拓扑会消息风暴 | 本方案 mesh 不转发；若做中继需 hop/TTL |
| 6 | discovery 里的 `ip` 字段不可信 | 多网卡/多网段时写错地址 | 接收方以 **UDP 源地址**为准，announce 内 ip 仅参考 |
| 7 | mDNS 跨平台不稳 | Windows 无 Bonjour 即失败 | UDP 广播默认，mDNS 可选 |
| 8 | 心跳未定义层级 | 各实现不一致 | 明确用 WS Ping/Pong + 应用层 `heartbeat` 双保险 |
| 9 | 大文件 64 KB 分块无断点续传 | 大文件中断需重传 | 元数据带 `total_chunks`，接收方记录进度，支持续传 |
| 10 | 接收文件无路径/大小约束 | 可被写入任意路径（安全问题） | 强制下载目录 + 文件名净化 + 大小上限 |

## 2. 产品定位与边界

**AgentLink 是什么**：一台机器上一个常驻的"消息总线进程"，负责把 A 机 Agent 的消息/文件，可靠地送到 B 机 Agent 或广播给所有节点。

**做什么**
- 节点自动发现（同一局域网，零配置）
- 自动建连、心跳、离线上线检测
- 点对点消息、群发消息
- 文件传输（元数据、分块、校验、确认）
- 本地 HTTP/WS 接口（供本机 Agent 调用与订阅）
- 结构化日志

**不做什么**
- ❌ 任务板 / 角色体系 / 工作流 / 业务编排（交给 Hermes 总控）
- ❌ 人类聊天 UI
- ❌ 公网穿透 / 中继服务器 / 跨网段路由
- ❌ 消息内容的解析与语义处理（payload 对 AgentLink 不透明）
- ❌ 持久化的历史消息库（只做短期存储转发，TTL 过期即丢）

## 3. 技术选型

### 3.1 语言 / 运行时对比

| 方案 | 单机产物 | 内存 | 跨平台 | 开发速度 | 结论 |
|------|---------|------|--------|---------|------|
| **Rust（已选）** | 单文件 ~3–6 MB | ~5 MB | 好 | 中 | ✅ 体积最小、无运行时依赖，贴合目标 |
| Go | 单文件 ~8–12 MB | ~10–20 MB | 交叉编译极简单 | 快 | 未选（产物更大） |
| Bun compile / Node SEA | 单文件 50–90 MB | ~40 MB+ | 好 | 很快 | 未选（不够轻） |
| Python + PyInstaller | 单文件 15–40 MB，启动慢 | ~30 MB+ | 一般 | 很快 | 未选（不适常驻） |

**选定 Rust**：`tokio` 异步运行时承载"每连接一任务 + 路由中心"，`tungstenite` 提供 WS 客户端/服务端，release 开启 LTO + strip 后单文件仅数 MB，各平台原生编译。

> 当前开发机（WSL）已通过 rustup 安装 stable 工具链。

### 3.2 关键依赖（Rust crate）

| 用途 | crate |
|------|-------|
| 异步运行时 | `tokio`（rt-multi-thread, net, sync, time, signal, io-util, fs, macros） |
| WebSocket | `tokio-tungstenite` |
| 本地 HTTP/WS | `axum` |
| 序列化 | `serde` + `serde_json` |
| CLI | `clap`（derive） |
| 日志 | `tracing` + `tracing-subscriber` |
| UUID / 随机 | `uuid`（v4） |
| 校验 / 签名 | `sha2`、`hmac` |
| 时间 | `time`（formatting + parsing，RFC3339） |
| base64 | `base64`（文件分块传输） |
| mDNS（可选） | `mdns-sd` + `local-ip-address`（feature `mdns` 引入） |

> mDNS 是编译期特性：`cargo build --features mdns`；默认构建只含 UDP 广播 + 静态 peers。

## 4. 总体架构

```
┌─────────────── 机器 A ───────────────┐         ┌─────────────── 机器 B ───────────────┐
│  本机 Agent (Hermes / 脚本 / LLM)     │         │  本机 Agent (Hermes / 脚本 / LLM)     │
│        │  HTTP/WS  (127.0.0.1)       │         │        │  HTTP/WS  (127.0.0.1)       │
│        ▼                             │         │        ▼                             │
│  ┌─────────────────────────────┐     │         │  ┌─────────────────────────────┐     │
│  │      AgentLink 本机服务      │     │         │  │      AgentLink 本机服务      │     │
│  │  ┌────────┐  ┌───────────┐  │     │         │  │  ┌────────┐  ┌───────────┐  │     │
│  │  │ 本地API │  │  路由器    │  │     │   WS    │  │  │ 本地API │  │  路由器    │  │     │
│  │  └────────┘  └───────────┘  │◄────┼─────────┼──┼─►└────────┘  └───────────┘  │     │
│  │  ┌────────┐  ┌───────────┐  │     │         │  │  ┌────────┐  ┌───────────┐  │     │
│  │  │ 发现器  │  │ 文件引擎   │  │     │         │  │  │ 发现器  │  │ 文件引擎   │  │     │
│  │  └────────┘  └───────────┘  │     │         │  │  └────────┘  └───────────┘  │     │
│  └─────────────────────────────┘     │         │  └─────────────────────────────┘     │
└──────────────────────────────────────┘         └──────────────────────────────────────┘
            ▲  UDP 广播 (8766) 互换 announce               ▲
            └────────────────────────────────────────────┘
```

**内部模块（单进程内）**
1. **本地 API 层**：HTTP + WS，只绑定 `127.0.0.1`。
2. **路由器 Router**：消息入口，判定点对点/广播，做去重、重试、离线暂存、ACK。
3. **节点表 PeerTable**：node_id → {name, ip, port, 连接状态, 最后心跳}。
4. **发现器 Discovery**：UDP 广播 announce/listen（+ 可选 mDNS）。
5. **连接管理器 ConnMgr**：对每个 peer 维护一条 WS，负责握手、心跳、断线重连、去重。
6. **文件引擎 FileEngine**：分块、校验、续传、落盘。
7. **配置 & 日志**。

## 5. 节点身份与命名

```jsonc
{
  "node_id": "a1b2c3d4e5f6",   // 稳定唯一：首次启动生成，持久化；或由公钥/机器指纹派生
  "name": "agent-PC-A"          // 展示名，可改、可重名（不用于寻址）
}
```
- 寻址一律用 `node_id`；`name` 只做人类可读展示和调试。
- 发送时允许用 `to: "agent-PC-A"`，由本地节点表把 name 解析成 node_id（仅当唯一时）。
- node_id 建议 12 位十六进制（随机，首次运行生成写入配置/数据目录）。

## 6. 发现机制

**默认：UDP 广播**
- 监听 `0.0.0.0:8766`（可配），加入广播。
- 启动即发一次 `announce`，之后每 5s 一次；退出发 `bye`。
- 收到 announce → **以 UDP 包源 IP 为准**记录对端地址 → 触发建连。
- 收到 `bye` → 立即标记离线。

```jsonc
// 发现报文（轻量、独立于消息协议）
{
  "discovery": 1,
  "action": "announce",          // announce | bye
  "node_id": "a1b2c3d4e5f6",
  "name": "agent-PC-B",
  "port": 8765,
  "ts": "2026-10-12T10:00:00Z"
}
```

**可选：mDNS**（`_agentlink._tcp.local`）+ **静态 peers 列表**（写死 `host:port`，用于广播被禁的网络）。

优先级：`静态列表 > UDP 广播发现 > mDNS`，三者结果合并去重。

## 7. 连接与拓扑

- **Mesh 全互联**：每个节点对每个已知 peer 维护一条 WS。
- **连接去重规则**：只有 `本地 node_id < 对端 node_id`（字典序）的一侧主动拨号，另一侧只监听，避免两条重复连接。
- **握手**：连接建立后立即交换 `hello`（含 node_id、name、协议版本 v、nonce、token 校验值）。
- **心跳**：
  - WS 层：每 10s Ping，20s 未 Pong 判死；
  - 应用层：每 10s 发 `heartbeat` 帧（带 ts），30s 无任何帧 → 标记离线并重连。
- **重连**：指数退避（1s→2s→4s…封顶 30s）。
- **规模建议**：Mesh 适合 ≤ 20 台。若未来机器很多，再引入"选一个 hub 节点做中继"模式（本版不做，但协议预留 `relay` 字段位）。

## 8. 消息协议

### 8.1 统一信封（在原文基础上补 `v`）

```jsonc
{
  "v": 1,                        // 协议版本
  "msg_id": "uuid-v4",           // 全局唯一，用于去重/ACK/关联
  "from": "a1b2c3d4e5f6",        // node_id
  "to":   "f6e5d4c3b2a1",        // node_id | "*"（广播）
  "type": "text",                // 消息大类
  "action": "send",              // 具体动作
  "payload": {},                 // 业务数据，AgentLink 不解析
  "ts": "2026-10-12T10:00:00Z",
  "reply_to": null,              // 可选：请求/响应关联
  "ttl_seconds": 300             // 可选：离线暂存存活时间
}
```

### 8.2 type / action 约定（可扩展）

| type | action | 说明 |
|------|--------|------|
| text | send | 点对点文本 |
| text | broadcast | 群发 |
| file | file_meta / file_accept / file_chunk / file_complete / file_done / file_error | 文件传输 |
| ctrl | ack / nack | 送达确认 |
| ctrl | heartbeat / hello / bye | 连接管理 |
| event | join / leave / peer_update | 节点上下线通知（本地订阅用） |

`payload` 完全由上层 Agent 定义，AgentLink 只透传。

### 8.3 可靠性语义（**本方案新增，原文档缺失**）

| 场景 | 语义 | 机制 |
|------|------|------|
| 点对点消息 | **at-least-once** | 发送方保存待确认表 → 收到 `ack` 删除；超时（5s）重发，最多重试 5 次；接收方按 `msg_id` 去重 |
| 广播消息 | **at-most-once** | 向每个在线 peer 各直发一份，不重试、不回环（mesh 不转发） |
| 离线对端 | **短期暂存** | 存入内存队列（可落盘），等对端上线后投递；超过 `ttl_seconds` 丢弃 |
| 接收端 | 幂等 | LRU 记录最近 N 个 `msg_id`，重复直接丢弃并回 `ack` |

> 只做"至少一次 + 去重"，不做严格 exactly-once（对 Agent 场景足够，且实现简单）。

### 8.4 发送示例

```jsonc
// 点对点
{ "v":1, "msg_id":"...", "from":"agent-1", "to":"agent-2",
  "type":"text", "action":"send", "payload":{ "content":"开始执行任务" }, "ts":"..." }

// 群发
{ "v":1, "msg_id":"...", "from":"agent-1", "to":"*",
  "type":"text", "action":"broadcast", "payload":{ "content":"全局配置已更新" }, "ts":"..." }

// 确认
{ "v":1, "msg_id":"...", "from":"agent-2", "to":"agent-1",
  "type":"ctrl", "action":"ack", "payload":{ "ref":"<被确认的 msg_id>" }, "ts":"..." }
```

## 9. 文件传输

### 9.1 流程（沿用原文顺序，补齐健壮性）

```
发送方                          接收方
  │ file_meta (id,name,size,chunk_size,total_chunks,sha256) │
  │────────────────────────────────────────────────────────►│
  │◄──────────────── file_accept {file_id, resume_from=0} ───│
  │ file_chunk × N (含 seq 与分块 sha256)                      │
  │────────────────────────────────────────────────────────►│
  │ file_complete {file_id, sha256}                          │
  │────────────────────────────────────────────────────────►│
  │◄──────────────── file_done {file_id, ok, saved_path} ────│
  │  任意阶段出错 → file_error {file_id, code, message}        │
```

### 9.2 元数据

```jsonc
{ "v":1, "from":"a1..", "to":"f6..", "type":"file", "action":"file_meta",
  "payload": {
    "file_id":"uuid", "file_name":"report.pdf", "file_size":10485760,
    "chunk_size":65536, "total_chunks":160,
    "checksum":"sha256:xxxx"   // 整文件校验
  } }
```

### 9.3 关键约束
- **下载目录**：接收方只允许写入配置的 `recv_dir`（默认 `<数据目录>/files`），**拒绝绝对路径与 `..`**，文件名做净化。
- **大小上限**：`max_file_size`（默认 100 MB），`file_meta` 阶段即拒绝超限。
- **分块**：默认 64 KB；每块带 `seq` + 分块校验，整文件用 SHA-256 收敛。
- **断点续传**：接收方按 `file_id` 记录已收 `seq`，重连时 `file_accept` 回报 `resume_from`。
- **落盘策略**：先写 `*.part`，校验通过后 `rename` 成正式文件（避免半成品被读取）。
- **并发**：同一对端同时文件数可配（默认 1），避免把消息通道饿死（文件走独立 WS？见 §11 说明）。

## 10. 本地接口

只绑定 `127.0.0.1`，需带 `X-Auth-Token`（本地 token，可与集群 token 不同）。

| 方法 | 路径 | 作用 |
|------|------|------|
| POST | `/v1/send` | 发消息（点对点 / 广播，用 `to` 区分） |
| POST | `/v1/send-file` | 发文件（传本地路径或上传字节流） |
| GET | `/v1/peers` | 查看节点及在线状态 |
| GET | `/v1/status` | 本节点状态、连接数、队列深度、版本 |
| GET | `/v1/health` | 存活探针（无需 token） |
| WS | `/v1/ws?client=<id>` | 订阅本机入站消息（推送 text/event/file 事件） |
| POST | `/v1/ack-inbox` | （可选）投递确认，配合至少一次语义 |

**调用示例**

```bash
# 点对点
curl -X POST http://127.0.0.1:8765/v1/send -H 'X-Auth-Token: xxx' -d '{
  "to":"agent-2","type":"text","action":"send","payload":{"content":"hello"}}'

# 群发
curl -X POST http://127.0.0.1:8765/v1/send -H 'X-Auth-Token: xxx' -d '{
  "to":"*","type":"text","action":"broadcast","payload":{"content":"notify all"}}'

# 发文件
curl -X POST http://127.0.0.1:8765/v1/send-file -H 'X-Auth-Token: xxx' -d '{
  "to":"agent-2","file_path":"C:\\data\\report.pdf"}'

# 订阅
# ws://127.0.0.1:8765/v1/ws?client=agent-2&token=xxx
```

> 说明：原文档用 `/send`、`/send-file`、`/peers`、`/ws`；本方案加 `/v1` 前缀以便版本演进。另一个与原文档的偏差：原文档设想"本地接口只绑 127.0.0.1、节点端口另用一个端口"，实际实现为**单监听器**（绑 `0.0.0.0:listen_port`），本地 `/v1/*` 用 local token 鉴权、节点 `/peer/*` 用 cluster token 握手鉴权；本机 Agent 仍走 `127.0.0.1`。

## 11. 安全模型

局域网半可信假设下的最小安全：

1. **集群 token**：所有节点共享一个 `cluster_token`（配置）。握手时校验，防止任意进程混入。
2. **帧签名**：每帧用 `HMAC-SHA256(cluster_token, node_id|msg_id|ts)` 附在头部，防伪造/篡改。
3. **防重放**：握手带 `nonce`，帧带 `ts`，超出时间窗（±60s）拒绝；`msg_id` 去重。
4. **本地 API 隔离**：仅 127.0.0.1 + 本地 token。
5. **不做**：TLS（留扩展位）、公网鉴权体系、证书管理。若网络不可信，可后续加自签 TLS（WS over TLS）。

**信任模式**（配置可选）：
- `strict`：必须匹配 cluster_token（默认）。
- `open`：局域网免密自动互信（调试/隔离网络用）。

## 12. 配置

文件名 `agentlink.json`（放数据目录或可执行文件同目录），支持 CLI 覆盖 + 环境变量。

```jsonc
{
  "v": 1,
  "node_id": "a1b2c3d4e5f6",
  "name": "agent-PC-A",
  "listen_port": 8765,
  "data_dir": "./data",
  "discovery": {
    "enabled": true,
```

## 13. 日志与可观测性

- 结构化日志（JSONL），滚动切分（按大小/天）。

## 14. 部署与打包

- **产物**：单个可执行文件，无运行时依赖。
- **Windows**：`agentlink.exe`；可用 `sc create` / NSSM 注册为开机自启服务。
- **Linux**：`/usr/local/bin/agentlink` + systemd unit（`Restart=always`）。
- **macOS**：launchd plist。
- **首次启动**：`agentlink init` 生成 `agentlink.json` 和随机 `node_id` / token。
- **升级**：替换二进制 + reload；协议 `v` 保证新旧兼容。

## 16. 里程碑（建议）

| 阶段 | 内容 | 产出 |
|------|------|------|
| **M0 骨架** | 项目结构、配置、日志、CLI、`/v1/health` | 能跑起的空服务 |
| **M1 发现+连接** | UDP 广播发现、握手、mesh 建连、心跳、`/v1/peers` | 两台机器能互相看到并保活 |
| **M2 消息** | 信封编解码、点对点、广播、本地 `/v1/send` + WS 订阅 | 文本消息端到端跑通 |
| **M3 可靠性** | ACK、重试、去重、离线暂存 | 断线重连不丢直发消息 |
| **M4 文件** | file_* 全流程、校验、限速/上限、续传 | ✅ 跨机传文件（独立连接/沙箱/大小限制已验证） |
| **M5 安全+打包** | token/HMAC/防重放、systemd/Windows 服务、`init` | ✅ 安全已实现；部署脚本见 `deploy/` |
| **M6 打磨** | mDNS、静态 peers、status 指标、文档 | ✅ mDNS `--features mdns`、静态 peers、指标、文档完成 |
| **M7 多Agent+人工视图** | agent_id 身份/定向投递、Agent 目录（fleet 同步）、tags、`/web`+`/v1/history` | ✅ 已实现并跨机验证 |

**MVP（建议先交付 M0–M2）**：两台机器互相发现、保活、双向收发文本 + 本地 HTTP/WS 接口。用最小闭环验证架构，再补可靠性和文件。

## 17. 风险与权衡

| 风险 | 说明 | 缓解 |
|------|------|------|
| UDP 广播被路由器/防火墙禁 | 跨网段或企业网常见 | 静态 peers 兜底；mDNS 补充 |
| Mesh 规模上限 | N² 连接 | ≤20 台足够；预留 hub 模式 |
| WS 上跑大文件阻塞消息 | 单连接拥塞 | 文件独立连接/独立 `file` 通道 |
| 多网卡 IP 判断错 | 机器有多张网卡 | 以 UDP 源地址为准，announce 内 ip 仅参考 |
| 协议过早复杂化 | 违背"最小" | 严格守住 payload 不透明 + 无业务逻辑 |
| Windows 防火墙首次拦截 | 需放行端口 | `init` 提示 + 文档说明放行 8765/8766 |
