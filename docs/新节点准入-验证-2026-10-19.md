# v0.6 P1 新节点准入 — 实现与验证（2026-10-19）

对应路线图 v0.6 §4.1：**新节点准入：bootstrap token + 硬件指纹双验证**。

与 mTLS（证书内核 / TLS 传输 / CA 自动分发，`docs/mtls-验证-2026-10-19.md`）
构成 §4.1 安全对子：**mTLS 解决「数据怎么加密传输」，准入解决「谁的机器有权入网」**。

默认**不启用**：`security.admission` 缺省关闭，老配置（无该段）逐字符回落 v0.5 行为
（cluster_token 单因素即可入网）。

---

## 1. 设计与威胁模型

准入是叠加在既有 cluster_token 之上的两个新因素——`security.admission.enabled=true`
后，一次握手必须**全部**通过：

| # | 因素 | 来源 | 说明 |
|---|---|---|---|
| 0 | 集群令牌 | `security.cluster_token`（既有） | strict 模式的既有必要条件，未变 |
| 1 | **bootstrap 令牌** | `security.admission.bootstrap_token` | 运维统一发放，与 cluster_token同等分发语义 |
| 2 | **硬件指纹** | `security.admission.allowed_hardware` 白名单 | 本机指纹必须被收录 |

裁剪模式（均在配置里显式表达，不搞隐式规则）：
- 只配令牌（白名单空）→ 单因素令牌。
- 只配白名单（令牌空/占位符）→ 单因素指纹。
- **都没配 → fail-closed：拒绝一切入网**（启动时打告警；`agentlink admission
  --enable` 在 CLI 层就拒绝无令牌开启）。

拒绝后果：连接立即关闭（`conn: handshake rejected (admission)`，含原因），
对端按既有断线重试；被拒节点**拿不到集群 CA**——闸门排在 CA 自动分发之前
（mTLS 的信任锚也不外泄给陌生机器）。

## 2. 硬件指纹（`src/admission.rs`）

- 纯 Rust、零新增依赖：优先操作系统级机器标识——Linux `/etc/machine-id`
  （或 `/var/lib/dbus/machine-id`）、Windows 机器 GUID（`reg query MachineGuid`）、
  macOS `IOPlatformUUID`（`ioreg`）；都没有时退回主机名。
- `SHA-256("agentlink|machine|<id>")` 取**前 16 个 hex 字符**（小写）；进程内
  `OnceLock` 缓存，同一台机器本次运行内恒定。
- 查询入口：`agentlink admission --status`（打印 self hw fp）与
  `GET /v1/admission`（Admin，`node_hardware` 字段）。

## 3. 协议（加性，`src/proto.rs`）

`Hello` 新增两个字段（老节点忽略；缺省不落 JSON）：
- `hw_fp`：本机硬件指纹（`Option<String>`）；
- `boot`：`HMAC-SHA256(bootstrap_token, node_id|nonce|v)`——复用 hello 自带的
  nonce 与签发格式，接收端在同一 nonce 上复验，无重放窗口。

## 4. 强制点与闸门语义（`src/conn.rs` / `src/file.rs`）

- **对等通道**（`/peer/ws`）：hello 分支在 cluster_token 校验**之后**、节点登记 /
  `agents` 更新 / **CA 分发之前**执行 `admission::gate`，未过闸即 `return false`
  断链。
- **文件通道**（`/peer/file/ws`）：`exchange_hello` 同样走 `gate`，建议路径无法
  绕过准入。
- **出站装配**：`Hello` 由 `admission::seal_hello` 统一盖章（对等会话的首发/
  改名重播、文件通道两端一致）；`open` 模式下也照发（指纹与 HMAC 本就无秘密）。

## 5. 管理面

```bash
# 查询（默认行为）：准入状态 + 本机指纹 + 白名单
agentlink admission --status

# 权威节点：发令牌、开启（须先配令牌）、收录新机器指纹
agentlink admission --enable --boot <TOKEN>
agentlink admission --allow <HW_FP>      # 可重复；--revoke 摘除；--disable 关闭

# 新机器旅程
agentlink admission --status             # ① 本机拿到自己的指纹
#   ② 在权威节点 --allow 收录该指纹
agentlink join <CLUSTER_TOKEN> --admission <BOOT_TOKEN>   # ③ 记录令牌（不自动开启本机 enforcement）
agentlink run                            # ④ 接入，A 侧双验证放行
```

- `GET /v1/admission`（**仅 Admin**；Operator/Viewer → 403）：`enabled` /
  `node_hardware` / `bootstrap_token_configured`（布尔，**不回显令牌本体**）/
  `allowed_hardware` 列表。
- 注意职责：`join --admission` 只写本机令牌；准入段的 `enabled`/白名单须与
  cluster_token 一同随集群分发（v0.6 运维分发；配置同步属后续项）。

## 7. 端到端冒烟（`tests/admission_smoke.py`，隔离端口，绝不碰生产 8765）

```
python3 tests/admission_smoke.py ~/agentlink-target/release/agentlink
SMOKE_RESULT 9/9
```

- S0 CLI：`admission --status` 默认 disabled，打印 16 位小写 hex 指纹；
- S1 基线：准入关闭 → 仅有集群令牌的节点互通（零行为变化）；
- S2 双验证全开：B 载令牌 + 指纹已入白名单 → 双向 online；
- S3 陌生节点 C（有集群令牌、无准入令牌）→ 拒（`handshake rejected (admission)`，
  成员表无 C）；合法的 B 同时仍互通；
- S4 指纹轴：白名单替换为不存在的指纹 → 令牌合法的 B 也被拒（日志含
  `硬件指纹未在准入白名单`）；恢复收录后放行（运维修复闭环）；
- S5 fail-closed：开启准入但令牌/白名单全缺 → 合法节点同样被全拒。

> 单机冒烟里各节点指纹相同（同一 machine-id），故指纹轴用「白名单摘除/恢复」
> 复现同一闸门路径；跨机部署时即天然区分每台机器。

另：`GET /v1/admission` 手工核验——Admin 令牌 200 且含 `node_hardware`；
无/错令牌 401；`/v1/health` features 仍为 `["events","redact","tasks",
"json-log","lockdown","hello"]`（= 0.5.9，逐字符不变）。

## 9. 边界与后续

- **指纹稳定性**：按 OS 机器标识计算，跨主机名/DHCP 变化稳定；主机名兜底只在
  标识缺失的极端环境生效。系统重装/VM 重建 ⇒ 指纹变化 ⇒ 需重新 `--allow`
  （把「换硬」当成一次新准入，符合语义）。
- **准入段分发**：与 cluster_token 同级的手工/运维分发；自动配置同步（或把准入
  并入 CA 分发式的对等 gossip）列为后续候选。
- **单因素模式**是显式裁剪：小集群可只发令牌；只配白名单等于「无运维发牌成本」，
  两者都不保证双因素强度——文档口径是「建议双配」。
- 后续候选：强制 mTLS `require` 模式、准入登记表（node_id↔指纹 binding 的
  运行期台账）、`top nodes` 色标等 CLI 完全体、Lease 差异上报、GitOps、熔断隔离。
