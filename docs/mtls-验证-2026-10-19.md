# v0.6 P1 mTLS — 实现与验证（2026-10-19）

对应路线图 v0.6 §4.1：**可选 mTLS：内置 CA 一键签发 + 24h 轮转（LAN 默认关闭、一键开启）**。

三波交付 + 追加固化：
- **第一波 证书内核**：内置 CA 一键签发/复用/轮转 + 指纹 + `agentlink mtls` CLI。
- **第二波 节点间 TLS 传输**：独立 TLS 监听端口 + 发现广播 + `wss://` 拨号 +
  双向 TLS（客户端证书校验）+ 文件通道同步加密。
- **第三波 CA 自动分发**：权威节点经已认证（strict）对等链路自动下发集群 CA，
  成员节点零文件拷贝领取并热启用 mTLS；冲突保护 + 离线不自建。
- **强制 require 模式（追加，§10）**：`mtls.require=true` 后拒绝一切明文对等链路
  （出站只拨 `wss://`、入站明文 `/peer/*` 403），把传输安全从「机会式」升级为可强制。

默认关闭时对现网/本地 API **零行为变化**（`/v1/health` features 逐字符不变、
本地 API 仍明文 HTTP、老节点混跑不破）。

## 1. 存储与产物

默认落在 `<data_dir>/mtls/`（`mtls.ca_cert`/`mtls.ca_key` 可改写 CA 路径）：

| 文件 | 内容 |
|---|---|
| `ca.pem` / `ca.key` | 集群根 CA（ECDSA P-256，自签，10 年） |
| `node.pem` / `node.key` | 本机节点证书（由 CA 签发，`ServerAuth+ClientAuth`）+ 私钥 |
| `node.expiry` | 节点证书到期时间（Unix 秒），用于轮转判定 |

节点证书的 SAN 含 `localhost` / `127.0.0.1` / `::1` / 主机名 / 本机全部网卡 IP，
使对端按 **IP 拨号**时标准 rustls 校验器即可通过名称校验（无需自写「跳过域名」
的危险校验器）。Unix 上私钥尽力收紧 `0600`。

**集群共享 CA**：一个集群必须共用同一 CA（CA 证书 + 私钥），各节点用同一 CA
**各自签发自己的节点证书**。三种取得方式（按推荐程度）：

1. **CA 自动分发（第三波，推荐）**：权威节点（`mtls.create_ca=true`，默认）建 CA；
   成员节点（`mtls.create_ca=false`）启动后经已认证的对等链路**自动领取**并热启用
   mTLS，无需拷贝任何文件。见 §6。
2. 把 `mtls.ca_cert`/`mtls.ca_key` 指向同一份共享文件（例如共享目录）。
3. 把首节点的 `mtls/` 目录分发给其他节点。

三者的信任语义一致（CA 私钥 = 信任域密钥，与 `cluster_token` 同级）。冒烟 S0
演示「共享 CA 就绪 → 两节点互信」，`tests/mtls_ca_dist_smoke.py` 演示「零拷贝
自动领取」。

## 2. 设计取舍：不引入 X.509 解析依赖

CA 仅作「签发者」使用——rcgen 的 `serialize_pem_with_signer` 只读取 CA 的
**issuer DN + 签名算法 + 私钥**（本模块自持常量 + 落盘私钥），故重签发节点
证书无需回读解析 CA 证书；到期时间单独落 `node.expiry`。只依赖 `rcgen`
（默认 `pem` feature），不启用 `x509-parser`。

## 3. 生成与轮转语义（`src/mtls.rs`）

- `load_or_create` / `load_or_create_opt(…, create_ca)`：CA 可读则复用，否则
  `create_ca=true` 时新生成整条链、`false` 时返回 `None`（成员待领取）；节点证书
  在轮转窗口外则复用，否则用现有 CA 重签（**CA 不变**）；节点证书缺失/损坏也沿用
  现有 CA。
- `adopt_ca(ca_cert, ca_key)`（第三波）：校验 PEM 可解析后落盘 CA、用该 CA 重签
  本机节点证书（用于 CA 自动分发领取）。
- 轮转判定：距到期不足 `cert_rotate_interval_seconds`（默认 6h）或已过期即重签。
- `rotate_node_cert()`：用现有 CA 立即重签并落盘（CA 指纹不变）。
- 默认：`enabled=false`、`cert_ttl_days=1`（24h）、`cert_rotate_interval_seconds=21600`、
  `listen_port=None`（= `listen_port + 1`）、`create_ca=true`、`ca_sync=true`、
  `require=false`（机会式）。
  `MtlsConfig` 手写 `Default`。

## 4. CLI 一键启用（`agentlink mtls`）

```bash
agentlink mtls              # 等价 --show：打印状态/角色/路径/指纹/到期
agentlink mtls --enable     # 生成/加载证书并把 mtls.enabled 置 true（一键开启，默认权威）
agentlink mtls --enable --member      # 以成员身份开启：不建 CA，启动后自动领取集群 CA
agentlink mtls --enable --authority   # 显式权威（等价默认）
agentlink mtls --enable --require     # 强制模式：拒绝一切明文对等链路（见 §10）
agentlink mtls --disable    # 写回 enabled=false（保留证书文件）
agentlink mtls --rotate     # 立即轮转节点证书（CA 不变）
```

`--member` 写 `mtls.create_ca=false`，`--authority` 写 `create_ca=true`（二者互斥）。
`--require` 必须与 `--enable` 同用（单独使用 clap 报错）。

## 5. 节点间 TLS 传输（第二波）

- **独立 TLS 监听**：`mtls.enabled=true` 时在 `0.0.0.0:<mtls.listen_port>`
  （缺省 `listen_port + 1`）额外起一个 axum-server/rustls 监听，**只**挂
  `/peer/ws` 与 `/peer/file/ws`。本地 API 与 `/web` 仍在 `bind` 上走明文 HTTP，
  本地客户端（curl/浏览器/CLI/老 agent）不受影响。
- **服务端**：`WebPkiClientVerifier`（信任锚 = 本集群 CA）+ 本机节点证书 ⇒ 要求
  并校验客户端证书（真双向 TLS）。
- **客户端**：只信任本集群 CA + 出示本机节点证书（`ClientConfig::with_client_auth_cert`）。
- **发现广播**：`DiscoveryMessage` 新增加性字段 `mtls_port`（老节点忽略）；开启
  mTLS 的节点据此广播 TLS 端口，对端按「同源 IP + TLS 端口」改走 `wss://`。
- **机会式升级**：仅当本节点开启 mTLS **且**对端广播了 mTLS 端点时才用 `wss://`，
  否则明文 `ws://`。混合版本/灰度期不断网（未支持 TLS 的对端仍明文）。
- **静态 peer**：`discovery.static_peers` 支持 `wss://host:port` / `mtls://host:port`
  前缀标记该端点为节点间 TLS 端点。
- **文件通道**：`open_file_ws` 按对端 mTLS 端点升级到 `wss://`，文件字节不再明文。
- 依赖：`rustls 0.23`（**ring** provider，禁 aws-lc-rs，避免 C/cmake，保
  windows-gnu 交叉编译与单二进制）+ `axum-server 0.7`（`tls-rustls-no-provider`）
  + `tokio-tungstenite` 开 `rustls-tls-webpki-roots`（自定义 CA 连接器）。

## 6. CA 自动分发（第三波）

目标：**集群共享 CA 零文件拷贝**——权威节点建 CA，成员节点启动即自动领取并热启用。

- **角色**：`mtls.create_ca=true`（默认）为权威节点，无 CA 时新建；`false` 为成员
  节点，无 CA 时进入「待领取」态（不建 CA），节点仍以明文正常运行。
- **识别**：`Hello` 新增加性字段 `ca_fp`（本机 CA 指纹，可空）与 `mtls_enabled`
  （是否参与 mTLS）。老节点忽略；缺失即按旧语义（无 CA、未参与）。
- **下发**：任意**已持有 CA** 的节点，在收到同信任域对端（strict 令牌握手通过）的
  hello 后，若对端 `mtls_enabled=true` 且 `ca_fp` 与本机不一致/缺失，则推一帧
  `ctrl/ca_sync`（CA 证书 + 私钥 PEM + 指纹）。故 CA 在网格中**顺带传播**（任何
  节点领到即可再分发给尚未持有的对端）。
- **领取**：成员收到 `ca_sync` 后，用 PEM **实算**指纹并与帧内声明比对（不信任
  声明），再 `adopt`：落盘 CA → 用该 CA 重签本机节点证书 → 热更新客户端配置并
  **热启动** TLS 监听（`watch` 通道，无需重启进程）→ 重新广播带新指纹的 hello。
- **冲突保护**：本地已有**不同** CA 时拒绝覆盖（返回 `Conflict`，不动任何文件并
  告警），避免信任域被静默替换/分裂。
- **就绪才广播**：只有真正持有 CA/TLS 配置时才在发现（UDP/mDNS）里广播 `mtls_port`；
  待领取的成员不广播，对端按明文连接（机会式降级），领取后自动开始广播。
- **安全边界**：`ca_sync` 仅在 `security.mode="strict"`（对端已证明集群令牌知识）
  下生效；帧含 CA 私钥，但仅发往同一信任域——与既有对称 `cluster_token` 模型一致
  （持令牌者本就可对任意 node_id 伪造握手），不引入额外越权面。CA 私钥等于信任域
  密钥，语义与 `cluster_token` 同级。

```bash
# 权威节点（默认）
agentlink mtls --enable
# 成员节点：不建 CA，启动后自动领取
agentlink mtls --enable --member
agentlink run
```

## 10. 强制模式（`mtls.require`，追加交付）

目标：关闭 §5 的机会式弱点——**开启后，明文对等链路一律不建立**（传输安全可强制）。

- **配置**：`mtls.require: bool`，缺省 `false`（机会式，默认零行为变化）。
  仅当 `enabled=true` 时实际生效（`require_enforced()`）；`require=true` 而
  `enabled=false` 属配置矛盾，启动时告警并按机会式处理（不崩，惰性）。
- **出站（拨号）**：`conn::open_ws` 前置纯函数闸门 `dial_allowed()`——强制模式下
  只允许 `wss://` 目标：对端广播了 mTLS 端点 **且** 本机 TLS 客户端就绪。缺一即
  **本地拒拨**（零网络开销），走 `debug!` 日志不刷屏；对端一旦广播 `mtls_port`
  即恢复可拨（无需重启）。明文 `host:port` 静态条目在强制模式下不再可拨，
  请写 `wss://host:port`。文件通道（`open_file_ws`）同走此闸门。
- **入站（监听）**：TLS 监听挂载 `axum::Extension(PeerTlsMarker)` 标记，明文监听
  不挂；`peer_ws`/`file_ws` 据此判定传输通道，强制模式下明文对等升级一律 **403**
  （`peer_transport_policy`），日志 `api: peer link refused`。**本地 API 与 `/web`
  完全不受影响**——管理面/网页仍是明文 HTTP（与本机 localhost 同级）。
- **部署次序（先灰度后强制，避免孤岛）**：① 全员 `mtls --enable`（机会式建连 +
  CA 自动分发/人工共享），② 确认 `/v1/peers` 全 online 且持有同一 CA，③ 逐节点
  `agentlink mtls --enable --require`。直接对「无 CA 成员」开 require 会形成孤岛：
  出站拒拨 + 入站拒明文 → 无法经对等链路领取 CA（启动时会告警提示）。
- **CLI**：`agentlink mtls --enable --require`（写 `mtls.require=true`）；状态行
  显示 `transport: require（强制 wss，明文对等被拒）` / `opportunistic`。

## 11. 边界与后续

- **弹性**：节点证书含全部网卡 IP；IP 变化由 24h 轮转自然刷新。
- **强制模式**：**已交付（§10）**。require 只作用于对等通道；本地管理面仍明文
  （与默认态一致，零迁移）。require 下节点证书 IP 未刷新时不会明文降级——直接
  拒拨/拒收（fail-closed），等轮转自愈。
- **CA 自动分发**：已实现（第三波）。仅 strict 模式生效；冲突拒绝覆盖；离线成员
  不自建 CA（需权威可达后领取，或人工放置 CA 文件）。
