## 1. 这份架构解决什么问题

AgentLink 本身只是总线：搬消息、搬文件，不解析语义。**"谁在网络上跑、各跑什么角色、
听谁的、出事找谁"——总线不规定，但用户第一天就会撞上。**没有官方答案，每台机器都会
自己发明一套，然后跨机协作时全部对不上。

本方案给出官方推荐的组织架构，重点解决三件事：

1. **新用户快速上手**：按机器数选 S/M/L 档，照抄角色表、命名、消息模板即可组网。
2. **运维统管**（核心痛点）：局域网升级 AgentLink、切换模型供应商、健康巡检——
   这些"没人认领的全网级杂活"由明确角色+固化协议承担，不再靠某个 agent 即兴发挥。
3. **角色边界**：编排、执行、运维、拍板四层分离，互不拖垮。

设计依据不是空想，来自本 fleet 三天实log（10-16～10-18）：0.5.8/0.5.9/0.5.10 三轮
全网滚动升级、10-18 全天百炼→OpenCode Go 全舰队模型切换（含 B 机 study 会话腿宕机、
由 B 机 agentlink 代办落地）、G-007 类同坑预警全网流转。本方案 = **把已经实战跑通的
非正式做法正式化、产品化**。

## 2. 五条设计原则

| # | 原则 | 来源/理由 |
|---|------|-----------|
| P1 | **一机一操作手**：每台机必须有且只有一个常驻 profile 充当"本机运维执行者"，它是本机唯一有权改本机 AgentLink 二进制/配置的通道 | 10-18 切模型实log：worker 会话腿宕机时，只有本机操作手能代办（B 机 study 链路 FAIL，agentlink 代办完成切换） |
| P2 | **一网一总控**：全网升级/切换/裁决收敛到一个编排角色，多编排并行=消息风暴 | 10-16 v0.4.19 去重护栏教训：编排侧两会话并行签发同版本 go，产生重复件与幽灵件 |
| P3 | **人类是唯一终极拍板**：agent 之间自治 ORD/ASK/ESC 闭环，但改政策、改窗口、熔断放行、争议裁决上报人类 | 现 fleet"候机主亲裁"白名单机制已验证 |
| P4 | **证据销账，不信自评**：一切"已完成"回报必须带实证（health 原文、sha 实算、grep 结果），编排侧现读复核后才记账 | 10-18 升级链全员执行"health 原文+sha 全串实算"；study@A 裁决班逐条"不信自评" |
| P5 | **正本走总线 git，敏感值永远带外**：规程/SOP/模板以 git 仓库正本分发；API key、token 一律不经明文消息正文（走 gitignore 的 secrets 或带外 fetch） | 10-18 换键实战：gokey_fetch 带令牌 + 指纹 fp 对账，明文 key 从未上总线 |

## 3. 角色模型

### 3.1 全景图

```
                        ┌─────────────────────┐
                        │   人类机主 Owner      │  拍板层：政策/窗口/熔断/亲裁
                        └──────────▲──────────┘
                                   │ 争议上报 / 重大事项请示
              ┌────────────────────┴────────────────────┐
              │        编排总控 Coordinator（全网 1 个）    │  政策层：发 ORD、裁决、
              │        （某主力机上的 worker profile 兼任） │  验收、SOP 正本维护
              └────────────────────┬────────────────────┘
                                   │ ORD / ASK / ESC / ACK（点对点+thread）
        ┌──────────────────────────┼──────────────────────────┐
        │ 机器 X                    │ 机器 Y                    │ 机器 Z
   ┌────┴─────────┐            ┌────┴─────────┐           ┌────┴─────────┐
   │ 本机操作手     │            │ 本机操作手     │           │ 本机操作手     │  运维层：
   │ Operator     │            │ Operator     │           │ Operator     │  升级/配置落盘/
   │ (常驻 profile)│            │ (常驻 profile)│            │ (常驻 profile)│  健康/代办执行
   ├──────────────┤            ├──────────────┤           ├──────────────┤
   │ worker×N     │            │ worker×N     │           │ worker×N     │  执行层：
   │ (业务 agent) │            │ (业务 agent) │           │ (业务 agent) │  干活、领卡、回报
   └──────────────┘            └──────────────┘           └──────────────┘
        ＋每机 watchdog 哨兵（cron/看门狗，机制非角色）：心跳、互盯、急件兜底
```

### 3.2 角色职责与红线

**① 人类机主（Owner）** — 拍板层
- 职责：定政策（成本档/窗口/纪律）、亲裁超白名单争议、批准熔断放行、带外分发密钥。
- 不做：日常消息路由、具体执行。

**② 编排总控（Coordinator）** — 政策层，全网恰好 1 个
- 职责：发起并终结全网级运维动作（升级 rollout、模型供应商切换、政策下发）；裁决班
  （处理 worker 的 ASK/ESC）；维护 SOP/模板正本；维护版本台账与 fleet 状态表；
  同坑预警的全网广播。
- 落位：**由一台最可靠机器上的 worker profile 兼任**（现 fleet 即 study@A），
  不新建独立进程。
- 红线：不直接改别机文件；一切改动经该机的 Operator 之手；同一 topic 同一版本
  只允许单会话签发（防双编排风暴）。

**③ 本机操作手（Node Operator）** — 运维层，每机恰好 1 个，常驻
- 职责：
  - 本机 AgentLink 二进制的升级执行（收 notice/go → 核 sha → 备份 → 换装 → 自检 → done）；
  - 本机配置/模型供应商落盘与验证（health 探测、探针回归）；
  - worker 会话腿宕机时的**代办执行**（代替宕机的 worker 改它的 profile 配置）；
  - 本机收件箱急件的兜底消费（看门狗轮询归它管辖）；
  - 本机台账落盘（upgrade-ledger 每机一份）。
- 落位：独立 profile（命名建议 `ops`；本 fleet 沿用既有的 `agentlink`）。
  **必须比任何 worker 都长寿**：只订阅总线+跑 cron，不接重业务。
- 红线：不做业务编排、不与其它机的 Operator 直接协商全网动作（跨机动作只听
  Coordinator 的 ORD）；不得把明文密钥写入总线消息。

**④ 业务执行者（Worker）** — 执行层，每机 0..N 个
- 职责：干活（编码/研究/学科任务/子 agent 编排）；消费发给自己的 ORD/ASK 并回证；
  自检班（lane/git/pool 状态定期上报）；缺粮/异常发 ESC。
- 红线：不互相发全网广播；升级窗口内按协议报备 ready/declined；
  出站消息遵守抬头标准（见 §6，违纪案例：study@B 抬头违纪×8 整改函）。

**⑤ 哨兵/看门狗** — 机制层，不算角色
- 每机 cron 看门狗（最坏 5 分钟兜底抓急件）＋ 跨机互盯（心跳超时报警）＋
  及时响应三件套（常驻桥 + wake hook + 清账纪律）。
- 报警去向：本机 Operator 先处置 → 处置不掉 ESC 给 Coordinator → 超阈值提示人类。

### 3.3 回答核心痛点：运维要不要独立专职角色？

**结论：全网级运维不需要独立"进程"，但需要独立"职责协议"。**

拆法：运维三权分离——
- **政策权**在 Coordinator（决定升不升、切不切、什么窗、验收标准）；
- **执行权**在各机 Operator（唯一能改本机的人）；
- **验证权**双向（Operator 自证 + Coordinator 现读复核，P4）。

这正是 fleet 过去三天实际跑通的模式（升级链、切换链都这么活下来的），只是从未被写成
官方协议。把它固化成 §4 的三个"运维工作包"，就是新用户可以直接抄的运维统管方案。
是否把 Coordinator 从 worker 里拆成独立 profile？——S/M 档不拆（拆了浪费一台对话位），
L 档（>10 机）拆成专职 fleet-ops worker（见 §5.3）。

**study@A 实战补强结论（10-19）：先脚本化，再谈角色。**巡检/催报/收账 90% 应是
零 LLM 确定性脚本（心跳/哨兵/看门狗/回执折叠），主控只读"需要判断力"的裁决卡。
运维独立成专职 LLM 角色是浪费；主控被机械杂事拖死的解法是**批量班+两段式**
（低价模型初筛+主力复核），不是加第四个角色（10-16 验收欠账 541 张恰是主控自身吞吐堵点）。
配置落盘类运维一律"正本下发+各机自执行+回执带可比对实值"，总控从不远程改别机配置。

### 3.4 三条横切职责（study@A 实战补盲，角色表初稿缺项）

四层角色方向成立，但缺三条横切职责定义——每条都是真金白银换来的：

1. **回执归属**：「在线 ≠ 读到 ≠ 已 ACK」三层必须分离设计，每类消息定死收讫责任方。
   血案 10-12 夜：来讯被静音化，需响应的请示躺了整夜没人接。
2. **写冲突裁决**：同仓多工作树/多写者必须指定**唯一正本写入通道**，否则未提交件会被
   别的进程强切抹掉。10-15 实烧：制度正本 10KB 无声蒸发。
3. **熔断拍板人**：工人 loop 空转烧钟点，必须有「**N 连零产物自动 ESCALATE**」熔断规则
   并明确拍板人，否则调度者永远在场也看不见。10-15 A1 空射案烧了数小时。

## 4. 三个运维工作包（统管协议）

每个包 = 触发条件 + 消息链 + 角色分工 + 回滚 + 台账 + 升级人类的路径。
消息全部点对点（at-least-once）、同链共用一个 `thread`、KIND 放 `action`。

### 4.1 UPD · 版本升级包（已产品化，v0.5.10 起 task_upgrader 承接）

```
Operator(B) 打包+tag → Coordinator 审批(或人类指定 pilot)
→ 逐机: NOTICE(预告,含sha/窗口) → INSTR(手册,reply_to) → GO(放行,带保护窗声明)
→ 目标机 Operator: 实算sha核对 → 备份 backups/v旧_时间戳 → 换装 → health 自检
→ DONE(带 health 原文+sha 全串,reply_to=GO msg_id)
→ Coordinator: ACK 销账(终结信号,收信方无需再回) → 台账 ledger 行 → fleet 版本表核对
```
- 保护窗：允许窗（如 08:00–22:00）+ 业务窗（如折扣活动冻结窗）双窗校验，GO 件里带
  窗声明；窗内收到 GO 也要拒（10-18 实拦案例：study 升级 GO 落在百炼 4 折窗内，
  Operator 按铁律 HOLD）。
- 异常路径：`sha 不符 → 中止+回报`；`hold → 不执行等改窗`；`包未落盘 → BLOCKED 急件`；
  `health 30s 不达 → 自动回滚 → ROLLED_BACK`。
- 顺序铁律：先 pilot 机 → 再其余 → 最后升 Coordinator 自己所在机（自升状态先落盘）。

### 4.2 MDL · 模型供应商切换包（10-18 实战固化，此前无文档）

```
人类/Coordinator 定策 → SOP 正本 commit 到总线 git（skills/<profile>/xxx-switch.md，带 tip hash）
→ 密钥带外分发（secrets 文件 gitignore / fetch 令牌+指纹 fp 对账 / 45min 取回窗）
→ 逐机 ORD(定向 worker,含正本路径+tip+验收标准"三证据")
→ 该机执行体落地（worker 在岗则 worker；腿宕机则 Operator 代办）
→ 回证：switch_done + 三证据（补丁 grep 计数 / 探针实调返回 / 默认档 grep）
→ Coordinator 逐条现读复核销账；未按时回证 → 催办 → 改派 Operator 代办
→ 新坑 → 同坑预警广播（G-007 机制：一机踩坑，全网自查回执）
→ 成本政策随后落地（MODEL-TIER 档位 + COST-POLICY 阈值，防切换后静默烧钱）
```
- 铁律零（最毒坑，10-18 study@A 事故复盘）：**切链路前先清点所有"守卫/看门狗/自动
  归位器"**，先 pause 守卫或改其 TARGET 再动手——跨 profile 硬锁看门狗曾 5 分钟内静默
  回滚切换结果，三次归位被顶回、md5 哨兵抓现行才定位。
- 铁律：明文 key 不上总线正文；旧供应商死透前不留单点（熔断哨：连续 N 次 402/401
  自动换道并 ESC）；每台机的双写检查（profile 层 + CLI 层凭据都要换）。
- 分发形态 = **三件套**：政策正本（文档）+ 机读配置表（roster/名册）+ 每机自查器
  （只读零模型、回执给可核数字）。单靠口头令 = 石沉大海（GO-SWITCH-SOP 验证：
  回执从口头变四组可比对数字）。
- 保护窗与回滚：fallback 链（同端点分模型独立额度堆叠，只在 429/额度尽/连接失败时
  触发——属保命不省电）+ 切换当天总控统一烟测（主链 + aux 压缩腿都打）+ 回滚 =
  **改正本一个字段跑一遍切换器**，不是逐机手改回去。错峰窗（到优惠时段批量切）
  适合成本驱动，不适合故障应急。
- 逃生道：上游供应商强制内容审查可**随机误杀长上下文会话**（qwen 系 10-18/19 实烧，
  同会话每轮必死）。选型时把"误杀后的逃生道"（换道/新会话 handoff）写进机制，别让
  唯一腿吊死——本方案 §9 请教件的答复即因此迟了 23 小时。

### 4.3 HLT · 健康巡检包

- 每 agent：及时响应三件套自查（新接入/换 agent 后重查）。
- 每机 Operator：cron 看门狗（5 分钟）抓 `upgrade_*/task_*` 急件；本机心跳落盘。
- Worker 自检班：定期报 `lane/git/pool` 三态；FAIL 即 ESC。
- 跨机互盯：peer 心跳超时 >15min → ESC Coordinator；Coordinator 核账后派单或上报人类。
- 台账：告警-处置-销案三段闭环（triage 单落 git，禁"仅回一句我重启过了"无实证收口）。

### 4.4 运维避坑清单（fleet 三天实log 用代价换来的教训，新用户必读）

| # | 坑 | 实证案例（10-16～10-18） | 规避条款 |
|---|-----|--------------------------|----------|
| L1 | **幽灵件**：正文放桥顶层 kind/content 被白名单静默丢弃，对端收到空 payload | 10-17 凌晨 B→A/C 连发 3 件全空，升级 go 实际未送达，A 侧坚持"未收到明确 go 不自行升级"才没出事故 | 出站正文一律 `payload={"content":…}` 嵌套（§6.3）；收方见空 payload 必回幽灵回执 |
| L2 | **并行唤醒会话抢跑**：同一急件拉起多个无头会话，runner 可能被跑两次 | C 机 0.5.3 同 trigger 出 3 条 ledger 行（1 实质+2 幂等重跑），备份被 keep=2 轮换挤掉 | 去重护栏：同 (sha,版本) 只执行一次 runner + `handled.jsonl` 登记 msg_id；done 以"合并记账"单条为准，他会话勿再补 |
| L3 | **notice 信封 sha 过期**：通告里写的 sha 与包正本不一致 | A 机升完 0.5.10 巡检发现信封值≠落盘实算值，发 SHA-MISMATCH-NOTE；B 按"三源现查"裁决：属 notice 过期，执行字节即正本，结案不回滚 | notice/instr/go 三件的 sha 必须发前现读正本重算；争议按裁决规则结案（落盘实算 > 历史信封），并留 SHA-VERDICT 回执链 |
| L4 | **版本回落**：旧目录 exe 被误拉起并抢赢监听口，health 报旧版而台账报新版 | A 机 10-16 升级后 health=0.4.12 而非 0.4.19：旧 v0.4.12 目录 exe 17:44 被手动拉起抢占 8765 | 升级后必查"运行进程 exe 完整路径 == 正本路径"；autostart 只指正本；旧版本目录改名或删除 |
| L5 | **防火墙公用配置文件断链**：WLAN 网络配置文件悄悄从 Private 翻 Public，inbound 全拦，节点掉线 6 小时 | D 机 10-18：B/A/C 拨入 D 均在 20~160s 被对端挂断，D 出站全进离线队列；无头会话遇 UAC 弹窗不能代点 | 掉线排查第一步 `Get-NetConnectionProfile`；**入站放行规则按端口**（TCP 8765/UDP 8766，Profile=Any）而非按程序路径；恢复走 `static_peers` 主动拨出；无头会话禁自改网络配置（不伪造 UAC） |

## 5. 分档组织模板（新用户照抄）

### 5.1 S 档：1–2 机（个人自用起步）

| 角色 | 落位 |
|------|------|
| Coordinator + Operator + Worker | **同一个 Hermes profile 兼任**（如 `dev`）；人类直连对话 |
| 哨兵 | 本机 cron 看门狗一条 |

- 起步动作：装节点→`/web/setup` 拿 token→agent 注册→接 bridge 三件套→完成。
- 运维链退化为"自我协议"：升级前自落台账、升后自验 health——格式与 M 档一致，
  日后加机器**无需改协议，只加角色**。这是分档设计的关键：协议同构，角色可拆。

### 5.2 M 档：3–10 机（OPC / 小团队，推荐标准形态）

| 角色 | 落位 | 数量 |
|------|------|------|
| Owner | 人类 | 1 |
| Coordinator | 最可靠那台机的一个 worker profile（建议命名 `coord` 或沿用工种名） | 全网 1 |
| Operator | 每机独立常驻 profile，命名统一 `ops`（fleet 存量沿用法：`agentlink`） | 每机 1 |
| Worker | 业务 profile（`dev`/`study`/…），可再 spawn 子 agent | 每机 0..N |
| 哨兵 | 每机 cron + 互盯 | 每机 1 |

- 寻址规范：`to=node_id` + `to_agent` 成对给；agent_id 严格用 profile 名，不加 IP 后缀；
  工人档案名跨机统一同名，靠 node_id 区分机器——**撞名是特性不是 bug**。
- 新用户最小 3 机样例（10-19 按 study@A 实战版修订，供文档演示/冒烟复用）：
  - 机1 `hub`：ops + coord（总控兼名册/政策正本维护）；机2 `work-a`：ops + dev；机3 `work-b`：ops + study。
  - 每台工人机配**本机零模型收发桥**（含收件去重折叠，防重复回帖风暴）。
  - 班次纪律：cron 一律 no_agent 脚本优先；agent 型班次限次自熄。
  - 首日三练：①coord 发起 upgrade_notice→ops 走完 DONE/ACK；②coord 下发一个
    model-tier ORD→dev 回三证据；③拔掉 dev 的桥，观察 HLT 包 5 分钟内 ESC 闭环。
  - 消息模板示例（抬头行严格按《消息模板标准》）：
    `【coord@hub → dev@work-a｜ORD｜10-19 09:00】` + 主题行 + `1) 2) 3)` 要点 + `ref: <msg_id>`。

### 5.3 L 档：10–100 机（中小团队商用形态）

- Coordinator 拆为**专职 fleet-ops profile**（不再兼 worker），且允许"1 编排 + N 域"
  分层：按楼层/项目组划分域，域内 worker 只认域主控，域主控只认总控（树状，杜绝网状广播）。
- Operator 数量不变（每机 1），但配置分发升级为 GitOps：模型/供应商/档位文件进 git，
  Operator 定时 pull + 漂移检测（config drift patrol），漂移即 ESC。
- 引入 v0.6 RBAC：Admin(人类)/Operator(ops)/Executor(worker)/Viewer(/web 只读 token)。
- 100 机估算（设计方案 §4.14 结论的推广）：广播仍可行（百毫秒级），但政策下发一律
  改"git 正本 + 逐机拉取"，不走消息洪峰。

## 6. 命名与消息规范（硬约束）

1. **agent_id = profile 名**，全网同名不同机靠 node_id 区分；`ops` 类角色名各机统一。
2. **抬头拼装进脚本**（如 al_send.py 的 mkhdr()），不靠人/LLM 记格式——study@B 抬头
   违纪×8 的整改实证：拼装权收回发送脚本后同类违纪归零。
3. 出站正文一律 `payload={"content":…}` 嵌套；出站必带 `from_agent`。
4. 闭环三信号：`ACK 收讫`（终结，无需再回）/ 直报实证 / `ESC`（处置不掉升级）。
5. 同主题多回合共用 `thread`（如 `upgrade-v0.5.10-B`），/web 星图按 thread 归组。
6. **防双编排**：同一 topic/版本单会话签发；发现重复 go 立即发去重护栏件
   （"同 sha+版本只执行一次 runner"）。
7. **消息双轨**（study@A 实烧）：对话腿（即时，给人和对齐）+ git 信箱（机读正典，派卡/
   裁决/存证）。要紧指令双轨并投、以 git 为存证——只走即时腿 = 对端编排器不读，
   实烧同一条令 WS 达而无人执行。
8. **任务与消息分离**：任务 = 卡片进信箱由工人自领；消息 = 讨论走对话腿。混发 = 永远没人领。
9. **超时催办与断粮自动补**：需要响应的消息 >15min 未回 = 事故级，由哨兵自动催办不靠人盯；
   队列见底由补班哨自动回血，看板上不许出现闲机。

## 8. 竞品对照：Paseo / 亿灵(Agent One) / NVIDIA PAIR

> 全文调研（含全部一手 URL 与待核实清单）见正本 `docs/竞品与行业案例调研-2026-10-18.md`。

| | Paseo | 亿灵 Agent One | NVIDIA PAIR |
|---|---|---|---|
| 是什么 | 开源多 coding-agent 编排 IDE（paseo.sh，~21k★）：daemon per machine + Hub 控制面 + Agent Profiles | 亿道(EMDOOR)软硬一体"AI 智能中枢"（2026-04 首发/WAIC 发布）：端侧优先、多设备任务接续 | 局域网"虚拟推理路由器"（NVIDIA，Apache-2.0）：mDNS 发现+mTLS，把 subagent 并发推理分发到空闲机器 |
| 组织形态 | 与我们最像：每机 daemon、agent 互发消息、Hub 集中编排；配置下发带 revision、**失败保旧** | 能力分层异构节点池 + 中枢调度（任务→执行节点） | agent 零改动，只看一个兼容端点；换模型/换引擎/扩节点全在 router 侧 |
| 运维统管 | Stable/Beta 双通道；但无集中升级各机 daemon 的机制 | 只有"可统一管理"宣传词，机制未公开 | Overview UI 健康巡检；无 fleet 式升级统管 |
| 与我们的关系 | **正面竞品**（编码向）。可借鉴：Hub 配置 revision+失败保旧、Agent Profiles 集中管选型、双发布通道 | 叙事对手但绑硬件；纯软件 P2P 总线位暂无直接对手 | **互补层非竞品**：它管算力落点，我们管消息与任务。可将 PAIR 式端点收编为一个可切换 provider |

**关键行业判断（调研核心发现）**：现有产品把"运维统管"分成两条互不覆盖的路线——
- **网关路线**（PAIR、LiteLLM）统管模型/供应商切换，不管软件升级；
- **控制面路线**（K8s Operator、Fleet、Paseo Hub、Tailscale）统管软件升级与配置下发，不管模型供应商。

**两家合一的"管理节点/运维角色"目前没有产品做实**——亿灵只有宣传词，Paseo 缺集中
升级。AgentLink 把两条路线合并进同一个运维角色（§3.3 的 Coordinator+Operator 协议）
是差异化机会，且总线天然顺路：期望版本上报、配置下发、心跳本来就是要搬的消息。

由此追加两条设计采纳（已并入 §4）：
1. MDL 包长期演进 = 可选"模型网关"服务（挂在 Coordinator 机，PAIR/LiteLLM 语义），
   全网 agent 指向单一端点，切供应商变成改网关一处配置——列入 v0.6+ 评估。
2. UPD 包增加"配置 revision 失败保旧"与 Stable/Beta 双通道（先 1 台 beta 机金丝雀）。

> 1) 命名与抬头：工号@机号 一行抬头【worker@A → worker@B｜kind｜MM-DD HH:MM】；工人档案名统一（跨机同名，靠node_id区分机器——撞名是特性不是bug，但寻址必须双字段to+to_agent）；kind只取枚举（ORD指令/ASK请示/ACK回执/DONE交付/ESC异常/NOTE周知/PING探活），语义放主题行；抬头必须是发送脚本在发送瞬间拼装的，人手打抬头=模板缺失。正文四段：抬头/主题≤40字/要点列表一行一事/ref尾注（给对方可机读核验的把手：msg id/commit/路径）。
> 2) 消息双轨：对话腿（即时，给人和对齐用）+git信箱（机读正典，派卡/裁决/存证用）。要紧指令双轨并投、git为存证——只走即时腿=对端编排器不读，石沉大海（我们实烧：同一条令WS达而无人执行）。
> 3) 3机最小配置：A=总控+名册/政策正本维护；B/C=各1常驻工人+本机零模型收发桥（含收件去重折叠，防重复回帖风暴）；班次全部no_agent脚本优先，agent型班限次自熄。
> 4) 三条可当模板的规则：①超时催办：需要响应的消息>15min未回=事故级，自动催办而非靠人盯；②任务与消息分离：任务=卡片进信箱由工人自领，消息=讨论走对话腿，混发=永远没人领；③断粮自动补：队列见底由补班哨自动回血，看板上不许出现闲机。
