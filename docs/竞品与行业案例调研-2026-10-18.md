## 一、竞品调研

### 1. Paseo(getpaseo/paseo)

**定位**:开源"agentic 开发环境/多编码 agent 编排器"——用一个界面同时跑 Claude Code、Codex、Copilot、OpenCode、Pi、Antigravity、Muse Code 等多个供应商的编码 agent,主打"parallel agents + 内置编排":agent 可以创建工作树(worktree)、启动其他 agent、跨供应商跨机器互发消息。
- 官网: https://paseo.sh/
- GitHub: https://github.com/getpaseo/paseo (约 21k stars,创建 2025-10)
- 编排文档: https://paseo.sh/docs/orchestration

**部署形态(本地/局域网友好度:高)**:自托管为核心卖点——"Agents run on your machine with your full dev environment"。架构是 **daemon(每台机器一个,拥有 agent 与工作区)+ 多客户端(桌面/原生 iOS/Android/Web/CLI)+ Hub(可选控制层)**。连接方式三种:SSH 隧道、官方端到端加密 relay、或**直接用 Tailscale 直连 daemon 的 100.x IP:6767**(文档明确给出局域网/跨网直连配置)。也可以把 daemon 跑在家庭实验室或云机上。
- 连接文档: https://paseo.sh/docs/connectivity
- Why 文档: https://paseo.sh/docs/why
- Hub 文档: https://paseo.sh/docs/hub

**组织架构与角色分工**:
- **编排层**:daemon 提供 MCP 工具目录(`create_agent`/`send_agent_prompt`/`list_agents`/`kill_agent`/`update_agent` 等)与 CLI(`paseo run/ls/attach/send/stop`),运行中的 agent 调用时自动成为调用者的 subagent,形成父子层级;父归档级联归档子。MCP 参考: https://paseo.sh/docs/mcp ;CLI: https://paseo.sh/docs/cli
- **角色模板 = Agent Profiles**:把 provider、model、thinking level、mode 存成 profile,配 "When to use" 注释,编排 agent 先读 profile notes 再委派(选型逻辑集中在一处,一处改全局生效)。
- **技能层**:官方 orchestration skills:`/paseo-handoff`(任务交接)、`/paseo-committee`(双 agent 独立分析)、`/paseo-advisor`(第二意见)。 https://paseo.sh/docs/skills
- **Hub(控制面)**:注册多台 daemon,接收 GitHub/Slack/Discord 事件按 trigger→workflow→step 在指定 daemon 上启动 agent;触发器配置(`.paseo/hub.yml`、`.paseo/workflows/*.yml`)放在代码仓库里、用 CLI 部署、有"活动配置版本(revision)"概念。 https://paseo.sh/docs/hub/concepts
- 插件生态有 24 个编排类插件(跨 daemon 互发消息的 Paseo Mesh、host 级 agent 巡检面板 Agent Monitor、Supervisor/Lead/Peer 团队等): https://paseo.sh/plugins/category/orchestration

**运维能力(升级、配置下发、监控)**:
- **双发布通道**:Stable + Beta(semver + prerelease tag,beta 无延迟推送、转正后 beta 用户即刻收到 stable)。 https://paseo.sh/docs/updates
- **配置下发 + 回滚保护**:Hub 同步配置 bundle 时逐项校验(daemon slug、filter、step id、schema…),**激活失败则保留上一个活动 revision**,Activity 继续反映最后可用配置——即"失败保旧"的声明式配置下发。 https://paseo.sh/docs/hub/concepts
- **监控/健康**:CLI `paseo ls -a`、`paseo usage`(配额/余额)、schedule run history(`schedule_logs`);daemon 重启后 background agent 存活。
- 配置入口:`~/.paseo/config.json` + `paseo reload`;模型供应商凭据用用户自己的订阅,平台不托管 key。

**开源/收费**:文档称 "Paseo is open source under Apache-2.0, with no telemetry, tracking, or required Paseo account"( https://paseo.sh/docs/why );GitHub 元数据显示 license 为 "Other"(具体文件以 repo 为准,待核实)。Hub 有 hosted 免费档("Create a free account; no card, does not expire")与 self-host 选项(内嵌数据库起步,可换 PostgreSQL)。https://paseo.sh/docs/hub

**与 AgentLink 的重叠与差异**:
- 重叠:局域网/自托管、多机、daemon 常驻、agent 间消息、编排角色、CLI/SDK。这是三家里**与 AgentLink 架构最接近、也最成熟的参照**,尤其"daemon per machine + Hub 控制面"分层、profile 集中管模型/供应商选择、Hub 配置版本回滚。
- 差异:Paseo 是**编码 IDE 替代品**(worktree/diff/PR/browser),编排对象限于 coding agent;不是通用消息总线,节点间通信走"客户端→daemon"星型+Hub,不是 P2P mesh;没有"节点升级统管"能力(各机各自装 daemon,updates 文档只讲发布通道,未讲集中升级——待核实是否有新特性)。AgentLink 的通用总线 + P2P mesh 定位差异化明显,但**恰好可以把 Paseo 的 Hub/profile 机制移植成自己的运维角色设计**。

### 2. 亿灵(内部代号 Agent One,亿道信息/亿道数码出品)

> 注意消歧:此"亿灵(Agent One)"是深圳亿道(EMDOOR)的软硬一体 AI 智能中枢,与阿里瓴羊的"AgentOne 企业级 AI 智能体服务平台"( https://www.lydaas.com/agentone )是两个不同产品,后者资料见附注。

**定位**:亿道面向"未来多设备智能协同"的 **AI 智能中枢/Agent 应用框架与执行中枢**:端侧模型与推理优先、隐私保护、多端设备(PC、手机、NAS、算力盒子、IoT)互联与数据互通。用户自然语言提任务,系统"统一接收任务、分配执行节点、调取所需数据、把结果返回请求端",任务可跨设备接续。
- 首发报道(2026-04-27,新浪财经转中关村在线): https://cj.sina.cn/articles/view/1747383115/6826f34b02003fid2
- WAIC 2026 发布(2026-07-20): https://www.icloudnews.net/a/120177.html
- 亿道官网新闻页: https://www.emdoordigi.cn/news/page_3.html

**部署形态**:本地/局域网优先——强调"断网情况下端侧模式可用"、私有数据不出设备;依托亿道自家"云、端、边、穿"硬件矩阵(AI 工作站、AI 服务器、AI NAS、Mini PC、平板、穿戴、工业 AIBOX/工控机),企业场景宣传"私有算力底座 + BMC 远程运维模块 + 7×24 运行"。**未见公开的独立软件部署文档或 API**。

**组织架构与角色分工**:按"任务需求和设备状态为任务匹配执行路径":简单任务本地快速完成、敏感任务端侧处理、复杂任务调近端算力或云端;各设备"根据各自能力承担不同角色",存储/推理/执行能力统一组织;NAS/工作站充当算力与数据底座,穿戴设备充当感知入口。属于**能力分层的异构节点池 + 中枢调度**模式。

**运维能力**:宣传口径为"可持续扩展、可统一管理、可快速部署""多模型集约化管理、算力弹性动态扩容"。具体的升级机制、配置下发、健康巡检、回滚**均未公开(待核实)**。

**开源/收费**:未找到开源仓库或定价页;目前形态更像**随亿道硬件出货的方案/产品**(待核实)。

**与 AgentLink 的重叠与差异**:
- 重叠:愿景高度相似——多设备、本地/端侧优先、统一任务中枢、跨设备任务接续、"可统一管理"的执行节点池。这是**中文市场里叙事最接近 AgentLink 的对手**。
- 差异:亿灵深度绑定亿道硬件矩阵(软硬一体销售),未见独立于硬件的通用消息总线或第三方设备接入协议;无公开 API/SDK/开源;调度粒度是"任务→执行节点",未见 agent 间对等通信协议。AgentLink 的纯软件、Rust 单二进制、任意设备 P2P mesh 是明显差异点;但在"统管运维角色"上亿灵同样只有宣传词、无落地机制,**两者都还没把运维角色做实——这是 AgentLink 的机会窗口**。

### 3. NVIDIA PAIR(Personal AI Router)

**定位**:**局域网"虚拟推理路由器"**——把家中/办公室同网段的 Windows/Linux/macOS 机器组成私有本地 AI 集群,把一个 agent(尤其多 subagent 工作流)的并发推理请求分发到空闲节点,解决"lead agent 拆多个 subagent → 单机 GPU 排队"的瓶颈。官方示例明确点名加速 NemoClaw、OpenClaw、Hermes 这类 agent(NVIDIA 博客的演示就是 Hermes Desktop + Ollama)。
- 产品页: https://www.nvidia.com/en-us/ai-on-rtx/personal-ai-router/
- GitHub: https://github.com/NVIDIA/Personal-AI-Router (Apache-2.0,约 1.6k stars)
- 技术博客(2026-09-03): https://developer.nvidia.com/blog/nvidia-pair-virtual-inference-router-expands-available-compute-on-your-local-network/
- FAQ: https://www.nvidia.com/en-us/ai-on-rtx/personal-ai-router/faq/
- 第三方报道: https://thenewstack.io/nvidia-pair-local-inference/

**部署形态**:每台参与机器安装 PAIR(Windows .exe / Linux .deb / macOS .dmg,也支持源码构建;x64+arm64,Win/Linux/macOS 节点可混编);**mDNS 自动发现 + 安全配对 + mTLS 加密**;支持引擎 Ollama、LM Studio、llama.cpp;硬件要求 RTX 20 系+/DGX Spark/Apple M4+。对 agent 完全透明:"The agent continues to see one connection while PAIR handles placement behind it",**无需改动 agent harness**。

**组织架构与角色分工**:
- 数据面:各节点跑本地推理引擎,向 router 上报"节点就绪、引擎状态、模型是否存在、GPU 利用率"。
- 控制面:router 暴露统一的 **Ollama 兼容 / OpenAI 兼容 / Anthropic Messages 兼容代理端点**,按上述实时状态把每个独立请求调度到合适的节点。
- 边界:不做 GPU 显存池化、不分片单模型跨机、不拆单个请求——纯"请求级路由"。
- 上层角色分工由 agent 自己负责(lead agent 拆任务给 subagents,PAIR 只管算力落点)。

**运维能力**:Overview UI 实时显示各节点 GPU/内存占用(健康巡检);模型/引擎在节点上的可用性是调度输入(相当于**把"模型供应商=本地引擎+模型文件"的映射集中到 router**);配对、节点纳入/移除有向导式管理。未见集中式版本升级/回滚机制(待核实)。
- 性能背书:5 subagent 演示,3 机 PAIR 集群 8m48s vs 单机 18m(约 2 倍+);双 5090 + Qwen3.6 35B 示例约 1.6x(https://developer.nvidia.com/blog/... 及 thenewstack)。

**开源/收费**:GitHub 仓库 Apache-2.0,beta 免费下载安装。

**与 AgentLink 的重叠与差异**:
- 重叠:局域网多机、自动发现、加密配对、统一入口、"节点能力感知调度"。PAIR 是**"模型/供应商切换统管"的最佳 LAN 先例**:agent 端只认一个端点,换模型/换引擎/扩节点全在 router 侧完成,agent 零改动。
- 差异:PAIR 只路由**推理请求**,不传递 agent 任务/消息、不管 agent 生命周期与节点上软件升级;它是 AgentLink 的**互补层**而非正面竞品(AgentLink 管"agent 间消息与任务",PAIR 管"模型请求落点")。AgentLink 的运维角色设计可直接借鉴其"统一兼容端点 + 状态驱动调度",甚至考虑与 PAIR 类网关互通(把 PAIR 端点作为一个可切换的 provider 源)。

## 二、行业通用模式(局域网/本地多机组织与运维)

### 1. Kubernetes:控制面-节点分层 + Operator 调谐 + Helm 回滚
- 架构:control plane(apiserver/etcd/scheduler/controller-manager)做全局决策并"检测与响应集群事件";每个 node 跑 kubelet(保证容器按 PodSpec 运行且健康)与 kube-proxy;生产环境控制面多实例高可用。https://kubernetes.io/docs/concepts/architecture/
- **Operator 模式**:把"人类运维专家"的知识编码成"自定义资源 + 控制环",声明期望状态、持续调谐,"automates deploying, backups, **handling upgrades of the application code alongside related changes such as … configuration settings**"——这就是"运维角色统管升级与配置切换"的最权威先例。 https://kubernetes.io/docs/concepts/extend-kubernetes/operator/
- 健康与回滚:node controller 负责"发现节点宕机并响应"(kubernetes.io 架构页);etcd 要求有备份计划;Helm 提供 `helm rollback <RELEASE> [REVISION]`,有 `helm history`、`--wait`、`--cleanup-on-fail`、`--dry-run`、`--history-max`(保留 N 个历史版本可回退)。 https://helm.sh/docs/helm/helm_rollback/
- 提炼:**期望状态声明 + 调谐环 + 版本历史 + 一次性回滚命令 + 灰度/金丝雀(通过分批次滚动)**,是节点软件升级统管的行业标准骨架。

### 2. Ansible(无 agent 推送) vs Salt(有 minion/控制面)
- Ansible:control node 通过 SSH 推送,**"Ansible is not normally installed on managed nodes"**(仅 ansible-pull 例外);inventory 文件描述节点与分组;playbook YAML 即配置下发单元。 https://docs.ansible.com/ansible/latest/getting_started/basic_concepts.html
- Salt:定位"open-source automation framework for remote execution, configuration management, and infrastructure orchestration — used by teams to **manage thousands of systems from a single control plane**",常驻 agent(master-minion)模型、事件驱动 reactor,适合实时健康巡检与批量下发。 https://saltproject.io/ 、 https://en.wikipedia.org/wiki/Salt_(software) (Apache-2.0;docs.saltproject.io 的架构专页多次改版 404,细节待核实)
- 提炼:局域网 ≤100 机两种都可行;**推送式(免安装、上手快、无心跳)** vs **常驻式(可订阅事件、可巡检、离线可检出)**。AgentLink 节点本来就常驻 daemon(消息总线属性),天然适合走 Salt 式"常驻+控制面",而不必学 Ansible 的纯 SSH 推送。

### 3. Fleet(FleetDM,设备/端点管理)
- 注册机制:中心 Fleet server + 每机安装 `fleetd` agent;**enrollment 用"fleet URL + enroll secret"打包**(`fleetctl package --fleet-url=… --enroll-secret=…` 生成 pkg/msi/deb/rpm),支持按 fleet 分组、各组独立查询与权限(Premium)。 https://fleetdm.com/guides/enroll-hosts
- 运维能力:REST API 集中管理配置(`/api/v1/fleet/config`)、host 软件清单、策略(policies)、MDM 命令;软件安装带**"Rolling back software install"**结果字段与 patch 策略(应用开着就跳过安装、下轮再试、可"提前 1 小时通知用户"),即安装级回滚与打扰控制;部署支持 on-prem/air-gapped。 https://fleetdm.com/docs/Using-Fleet/REST-API
- 开源/收费:核心开源 + Premium 商业档(API 返回中可见 `license.tier: premium`)。
- 提炼:**enroll secret + 分组(fleet)+ 查询式巡检 + 策略合规 + 补丁窗口/回滚**——中小团队档的"运维角色统管升级"可直接照这套语义设计。

### 4. Tailscale:薄控制面 +  thick 数据面(P2P mesh,与 AgentLink 形态最像)
- 定位:"Zero Trust identity-based connectivity platform",客户端装到每台设备,控制面只做身份/策略,**数据面 P2P 直连**;管理用 Web admin console(Machines 页移除/批准节点),稳定 `100.x.y.z` 地址由控制面分配,管理员可改 IP pool;subnet router/exit node 给特殊节点赋予转发角色;功能预览采用邀请码/白名单灰度(Owner/Admin/IT admin 角色分级)。 https://tailscale.com/docs 、 https://tailscale.com/kb/1033/security(重定向后内容)、 https://tailscale.com/kb/1222/client-updates
- 提炼:**"控制面可以很小甚至托管,数据面保持本地直连"** 与 AgentLink"LAN P2P mesh"完全同构;其 admin console 的角色(批准设备、ACL、分组 tag)就是"运维统管"的极简样板;灰度(邀请码)与"移除即回收身份"值得抄。

### 5. LiteLLM:模型/供应商切换的集中统管先例
- 开源统一网关:**单端点调 100+ LLM**,SDK Router 带重试/跨部署 fallback;自托管 **LLM Gateway(Proxy)** 提供 virtual keys(按 key/team/user 的预算与限流)、集中日志、guardrails、成本追踪、Admin UI;还扩到 MCP 与 A2A agent 网关。 https://docs.litellm.ai/docs/
- 提炼:对 AgentLink 最关键的一条先例:**模型供应商切换 = 网关层改配置,client/agent 零改动**。"运维统管模型/供应商配置"在业界已有成熟语义(key 分发、预算、fallback 链、按团队分 policy)。

### 6. AI coding agent fleet 的角色分工范式
- **Claude Code subagents**:每个 subagent 独立上下文窗口 + 自定义 system prompt + 受限工具集 + 独立权限;可按角色指定模型(把探索类 subagent 路由到更便宜的 haiku 控成本);内置 Explore/Plan/general-purpose 角色;支持用 plugin 把 subagent 定义分发到团队(官方措辞 "Distribute subagents with plugins … to share subagents across teams")。 https://code.claude.com/docs/en/sub-agents
- **Paseo 编排**:lead agent 通过 profiles(notes 描述专长)选 specialist;committee/advisor/handoff 固定角色工作流(见上文第 1 节)。
- **Devin**:一人并行管多个 Devin session(云端),本地 Devin CLI 可 `/handoff` 把长任务交给云端 Devin;有 Administrator 权限体系与 Individual/Teams 付费档。 https://docs.devin.ai/get-started/devin-intro
- **CrewAI**:role/goal/backstory 三元组定义 agent,`allow_delegation` 控制委派,`max_rpm/max_iter/max_execution_time` 是运维型限额参数,JSONC 文件即配置分发单元。 https://docs.crewai.com/concepts/agents
- **AutoGen**:分层 AgentChat(会话)→ Core(事件驱动、可扩展到 GrpcWorkerAgentRuntime **分布式 agent 运行时**),Studio 提供无代码原型 UI。 https://microsoft.github.io/autogen/stable/
- 提炼:agent 圈通行的是**"编排(lead/orchestrator)—执行(specialist/worker)—评审(advisor/reviewer/committee)"三角色 + 集中定义的 profile/role 配置**;但"平台软件自身升级 + 模型供应商切换"这一层在 agent 产品里普遍缺位(见结论)。

## 三、提炼:对 AgentLink "官方推荐局域网 agent 组织架构" 的启示

### 3.1 角色分层(业界收敛形态)
| 层 | 业界样板 | AgentLink 对应 |
|---|---|---|
| 控制面/运维角色(可单实例) | K8s control plane、Fleet server、Tailscale admin console、Paseo Hub、Salt master | "管理节点/运维 agent":设备批准(enroll secret)、ACL、分组、期望版本、配置/模型 policy |
| 编排角色 | Paseo lead agent、Devin、Claude Code 主会话 | 任务拆解与委派 agent,读取集中定义的 profiles |
| 执行角色 | kubelet 上的 Pod、PAIR 节点、CrewAI worker | 各机上的执行 agent(消息总线 P2P 参与方) |
| 观测/评审角色 | Fleet policies、Auto Resume/Advisor、Agent Monitor 插件 | 独立巡检 agent + 评审 agent(只读权限,学 Claude Code 的 tool deny) |

个人档 = 一机兼四层;一人公司 = 拆出编排;≤100 机团队 = **必须显式指定 1 台管理节点承担运维角色**(Fleet/Tailscale 语义:enroll/批准/tag 分组/期望状态),这正是当前 AgentLink 缺失的统管入口。

### 3.2 配置与版本分发机制
- **声明式期望状态 + 调谐**(K8s Operator):管理节点记录"全网期望 AgentLink 版本/配置 revision",节点对比自身状态上报,不一致才动作;而非脚本逐个推。
- **配置带版本、失败保旧**(Paseo Hub):每次下发是一个 revision,校验失败自动保留上一活动 revision——天然的坏配置熔断。
- **发布通道**(Paseo Stable/Beta、Tailscale 邀请码灰度):1..N 台 beta 节点先行,验证后全网;≤100 机场景"金丝雀 1 台"成本极低。
- **回滚保护**(Helm rollback/helm history/--wait/--cleanup-on-fail):保留最近 N 个版本产物,一条命令回退,回退需等待健康确认。Rust 单二进制恰好使"多版本共存 + 原子换 binary + 重启回退"比 K8s 还容易实现。

### 3.3 健康巡检
- 心跳 + 版本 + 模型可用性上报(Salt minion / PAIR 节点状态四要素:就绪、引擎、模型、负载);node controller 式"失联即事件"(K8s);查询式合规检查与 policy 计分(Fleet)。

### 3.4 "运维角色统管升级 + 模型/供应商切换"的先例——有,且分两条路线
1. **网关路线**(LiteLLM Proxy、NVIDIA PAIR):把模型/供应商切换收敛到一个兼容端点(OpenAI/Anthropic 格式),全网 agent 只指向网关;运维角色改网关的 deployment/fallback 链即完成全网点切换,还附带按 key/团队预算、限流、审计。局域网私有化 = 在管理节点跑一个 PAIR/LiteLLM 式路由(axum 实现完全在 AgentLink 技术栈射程内)。
2. **控制面路线**(K8s operator、Fleet、Tailscale admin、Paseo Hub):软件自身升级与配置以"期望状态 revision"经控制面下发,节点侧 agent 调谐执行,失败保旧 + 一键回滚。
- **两条路线在现有产品里是分离的**(PAIR/LiteLLM 不管软件升级;Fleet/K8s 不管模型供应商)——**AgentLink 把两者合并进同一个"管理节点/运维角色"是差异化机会**,且技术上顺路:消息总线本身就能承载"期望版本上报 + 配置下发 + 心跳"三类消息,模型网关可作为管理节点的一个可选服务。
