# chaos 故障注入第二波验证（2026-10-20，v0.7 §6.4）

路线图 v0.7：「chaos 套件：kill-node / latency / disk-fill【§6.4】」。
kill-node 第一波（节点失联自动回收）已交付；本包补齐 **latency** 与
**disk_full** 两个可验证子集：

- `latency`：`Router::send` 出口前固定 sleep，模拟总线/网络延迟；
- `disk_full`：`TaskStore::append` 直接返回 IO 错误（模拟 ENOSPC），
  **不实际写满磁盘**，用于验证 journal 失败回滚与恢复；
- 只允许 Admin 经 `POST /v1/mesh/chaos` 注入，`DELETE` 提前解除，TTL
  到期自动失效；运行态不持久化；
- 缺省 `mesh.chaos.enabled=false`，关闭态 `Router`/`TaskStore` 的检查为
  常数级、零延迟/零注入，行为不变。

## 1. 配置

```jsonc
"mesh": {
  "chaos": {
    "enabled": true,
    "max_duration_seconds": 60,   // 单次注入上限 1-3600，缺省 60
    "max_latency_ms": 5000        // latency 上限 1-60000，缺省 5000
  }
}
```

- `enabled=false` 时 POST/DELETE 返回 403，GET 仍可读（enabled=false、
  active=[]）；配置校验在 `Config::validate`。
- 注入参数：`kind` ∈ {`latency`,`disk_full`}；`duration_seconds` 缺省 5，
  范围 `1..=max_duration_seconds`；`latency` 必填 `latency_ms`
  `1..=max_latency_ms`，`disk_full` 忽略该字段。
- 同一 kind 重复注入覆盖旧值；不同 kind 可并存（例如同时延迟 + 磁盘错）。

## 2. 接口与语义

```http
POST /v1/mesh/chaos     （Admin）
{"kind":"latency","duration_seconds":3,"latency_ms":400}
→ {"ok":true,"active":[{"kind":"latency","remaining_seconds":2,"latency_ms":400}]}

GET /v1/mesh/chaos      （Admin）
→ {"ok":true,"enabled":true,"max_duration_seconds":60,"max_latency_ms":5000,
   "active":[...]}

DELETE /v1/mesh/chaos   （Admin）
→ {"ok":true,"active":[]}
```

- Operator/Viewer 调治理面 403（与 `/v1/mesh/status|quota` 同口径）。
- `latency`：所有经 `Router::send` 的出站帧（含本机投递、控制面/
  heartbeat）在签名/投递前 sleep；`latency_ms` 为固定值，无抖动/丢包。
- `disk_full`：`TaskStore::append` 在任何写操作之前返回
  `io::Error("chaos: simulated disk full ...")`；调用方按真实磁盘错误走
  回滚，API 映射 500 `task journal append failed`，任务不落表。
- TTL 用 `Instant`，查询/派发时惰性清理；到期后自动恢复，无需人工。
- 审计：`chaos.start`（kind/duration/latency_ms，actor=角色）与
  `chaos.stop`（scope=all）；仅 `security.audit.enabled=true` 时入链。
- 不写 webhook、不写 history，避免 chaos 自身放大流量。

## 3. 改动面

- 新增 `src/chaos.rs`：`ChaosKind` / `ChaosConfig` / `Chaos`（单 Mutex
  故障表、TTL、snapshot）+ 3 单测（过期、覆盖/清除、校验边界）。
- `src/config.rs`：`mesh.chaos` + validate。
- `src/router.rs`：`Router.chaos: Arc<Chaos>`；`send()` 在 lockdown 检查后、
  签名前 sleep（不持 Router 锁）。
- `src/taskstore.rs`：`TaskStore.chaos: Option<Arc<Chaos>>` + `set_chaos()`；
  `append()` 写前检查 `disk_full`（测试/默认 None，无注入）。
- `src/api.rs`：`build_mesh` 接收 Router 的同一 `Arc<Chaos>` 并交给 store；
  `/v1/mesh/chaos` GET/POST/DELETE；Operator 排除；`chaos.start/stop` 审计。
- `src/main.rs`：装配时把 `router.chaos` 传入 `build_mesh`。
- 单测 183/183（原 180 + chaos 3）。

## 5. 边界与残留

1. **disk_full 不是实际磁盘写满**：只拦 task journal 的 `append`；消息
   journal、task 快照、audit、文件传输仍可写。真实 ENOSPC 会影响全部
   IO，本注入只覆盖任务引擎最关键的落盘点。
2. **latency 作用于所有出站帧**：包括 heartbeat/ctrl；注入值接近
   ack_timeout/heartbeat 间隔时可能触发假失联/重连。请在 TTL 内使用，
   生产建议 ≤ 数百 ms。
3. **进程本地、非集群级**：chaos 表在单节点内存，不随 relay/peer 扩散；
   多节点演练需逐节点注入。
4. **固定延迟，无抖动/丢包/乱序**：不是 `tc netem` 的完整网络模型；
   不做概率注入（激活期间 100%）。
5. **TTL 精度为秒**：`duration_seconds` 整数，剩余时间按整秒展示；
   `Instant` 不持久化，重启即清空。
6. **Admin 可用性风险**：开启 `mesh.chaos` 后，拥有 Admin token 的人可
   短时制造 500/延迟；缺省关闭 + 上限 + TTL 是最小防线，生产应配合
   网络 ACL 与审计告警。
7. **审计只有 start/stop**：不记录每个被延迟/被拒的请求；需要逐请求
   证据时结合 access log 与 `task journal append failed` 日志。
8. **不覆盖引擎内存状态**：disk_full 期间引擎表可能保留已应用的行并在
   回滚路径撤销；不会造成 journal 数据损坏（写前失败），但会持续打
   error 日志。
9. **无定时/编排**：不支持 cron 式“每 5 分钟注入 10s”，也不支持
   kill-node 与本包的组合编排；后续 chaos 套件可加。
10. **仅 Linux/单进程语义**：不涉及 cgroups/Job Objects；进程隔离仍
    是 §5.4 后续。
