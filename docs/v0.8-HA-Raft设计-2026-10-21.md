# v0.8 HA / Raft 设计稿（RFC，2026-10-21）

> 状态：**已评审待实施**。本稿是 v0.8 的设计基线，M1~M5 按本稿分阶段落地。
> 与既有文档的关系：v0.7 的 OIDC/配额/审计/任务引擎等模块语义**不变**，
> 本稿只回答「多副本部署时哪些状态必须一致、怎么一致、坏了怎么办」。

## 0. TL;DR（决策摘要）

| 决策 | 结论 | 备选与否决理由 |
|---|---|---|
| D1 一致性方案 | **节点内嵌 Raft**（自研，传输复用 peer WS） | 否决外挂 etcd/consul/TiKV：违反「单二进制、零运行时依赖」；否决 quorum store：外部进程 + 运维负担 |
| D2 复制对象 | **按命名空间分区的 KV 状态机**（任务/配额/审计/OIDC session 各自命名空间） | 否决「直接复制文件目录」：跨节点文件一致性与幂等恢复都难做 |
| D3 节点规模 | **少数派投票成员（≤9，奇数）+ 只读学习者（learners）** | 否决 20 节点全投票：全量复制 20 份在 LAN 也浪费；learners 只收日志不投票，扩容不影响 quorum |
| D4 读一致性 | 写路径线性一致；**读默认 leader 强一致**，UI 概览可显式降级为本地读 | 否决「一律本地读」：配额/任务状态会读到旧值，产生超发与误判 |
| D5 传输 | 复用既有 peer WebSocket，新增 `kind=ctrl, action=ha_*` 帧 | 否决另开端口/协议：多一套 TLS/鉴权/心跳，故障面翻倍 |
| D6 存储 | 日志 + 快照落 `<data_dir>/ha/`，追加写 + fsync；**不引入 SQLite** | 否决 SQLite：带 C 依赖，破坏纯 Rust/交叉编译 |
| D7 降级 | 无 quorum → 自动进入既有 **degraded（只读/standalone）** | 与 v0.7 降级模式统一，不新增第二套降级语义 |
| D8 开关 | `ha.enabled=false` 缺省，**默认态行为与今天逐字相同** | 与 mesh/gitops/oidc 等既有段一致的向后兼容纪律 |

## 1. 背景与目标

### 1.1 现状（v0.7）

AgentLink 已经是「20 台机器的 LAN 消息总线 + 任务引擎」：mTLS 节点间传输、
Lease 心跳、任务引擎（journal + checkpoint + LWW）、per-namespace 配额、
不可变审计 hash 链、ABAC/guardrails、GitOps、OIDC SSO、混沌注入、SLO 指标。

但**所有关键状态都是节点本地内存/本地文件**：

| 状态 | 现状 | 单机挂掉的后果 |
|---|---|---|
| 任务定义与状态（`taskstore`/`taskengine`） | 本地 journal + checkpoint | 任务丢失、状态回退 |
| 调度与在飞计数 | 本地 `scheduler` | 重复派发、幽灵任务 |
| per-namespace 配额 | 本地滑动窗口 | 超发（每节点各算一份） |
| 审计 hash 链 | 本地追加链 | 链断裂、无法证明顺序 |
| checkpoint（任务迁移） | 本地 | 迁移中断 |
| OIDC 浏览器 session / state | 本地内存 | 多副本下 login 与 callback 必须粘同一节点；滚动升级即掉线 |
| Mesh 拓扑、邻居表、指标 | 本地 | 正常（本就各视角不同） |

### 1.2 目标（v0.8）

1. **节点挂掉不丢状态**：任务、配额、审计、SSO 会话在多数派存活时可继续；
2. **不重复派发**：同一任务在集群内只被一个节点执行（leader 派发）；
3. **配额全局一致**：per-namespace 配额按集群维度限流，而不是每节点各算；
4. **SSO 多副本可用**：任意副本都能完成 login/callback/刷新；
5. **运维可控**：HA 可开可关；关闭时行为与 v0.7 完全一致；开启但未成 quorum
   时自动降级为只读，绝不「脑裂双写」。

### 1.3 非目标（明确不做）

- 不做跨机房多活/异地容灾（LAN 场景，无需）；
- 不做分布式事务（2PC/XA）；
- 不替换现有业务消息总线（业务消息仍是 at-most-once 尽力投递语义）；
- 不做容器编排（K8s Operator）——仍是裸机/单二进制；
- 不引入外部数据库/缓存/共识服务（单二进制铁律）。

## 2. 一致性模型

### 2.1 哪些必须线性一致

| 操作 | 一致性要求 | 原因 |
|---|---|---|
| 提交任务（写任务定义） | 线性一致（leader 写入 + 多数派复制） | 否则同一 task_id 可能被两节点各写一份 |
| 任务状态迁移（running→succeeded） | 线性一致 | 否则状态机分叉，checkpoint 不可信 |
| 配额扣减 | 线性一致 | 否则 N 个节点各放 N 份，超发 |
| 审计追加 | 线性一致 + 链头一致 | 审计要能证明全局顺序 |
| SSO session 创建/吊销/续期 | 线性一致 | 否则 A 节点登出、B 节点仍有效 |
| 调度派发（谁执行） | leader 单点决策 + 幂等 | 执行权唯一 |

### 2.2 哪些允许最终一致

| 状态 | 理由 |
|---|---|
| Mesh 拓扑 / 邻居表 / 在线状态 | 本质是各节点视角；强一致反而失真 |
| Lease CPU 采样 | 采样类指标，容忍滞后 |
| SLO 指标 / 事件流 | 观测类，允许迟到 |
| 断路器 / chaos 注入 | 节点本地运维动作，故意不复制 |
| 审计与配额的**读**（UI 概览） | 可降级为本地读（显式标注「可能滞后」） |

### 2.3 失败语义

- 写入在**多数派复制成功**前不返回成功（默认线性一致写）；
- 多数派不可用时写入**拒绝**（503），**不**本地落盘后假装成功；
- 读在无 leader 时默认**拒绝**（503），UI 概览类可显式走本地读；
- leader 崩溃 → 新 leader 接管，未提交日志丢弃，已提交日志保留。

## 3. 架构

### 3.1 角色与状态

```
Follower ──(选举超时)──> Candidate ──(拿到多数票)──> Leader
   ^                        |                          |
   └────(收到更高 term)─────┴────(发现更高 term)───────┘
```

- **term**：单调递增的逻辑时钟；任何 RPC 携带 term，收到更高 term 立即退为
  follower 并持久化；
- **投票约束**：每个 term 每节点最多投一票（持久化 `voted_for`），候选日志
  必须**至少同样新**（`last_log_term`/`last_log_index` 比较）才能拿票；
- **日志**：`(index, term, command)` 追加序列；`prev_log_index/prev_log_term`
  校验，失败则回退重试（`next_index` 递减）；
- **提交**：多数派 `match_index > commit_index` → 推进 `commit_index`；
  **仅当 leader 的 `term == currentTerm` 时才能直接提交**（Raft §5.4.2），
  避免旧 term 的日志被误提交；
- **应用**：follower 按序 apply；`applied_index <= commit_index`。

### 3.2 节点构成（D3）

```
voting members (奇数, ≤9)   n1 n3 n5      ← 参与选举与 quorum 计算
learners (只读复制)          n2 n4 n6...   ← 只收日志，不投票、不算 quorum
```

- 20 机商用形态：**5 个投票成员 + 15 个 learner**；
- learner 落后不影响 quorum，可随时「提升」为投票成员（成员变更走 joint
  consensus，见 §3.5）；
- 投票成员必须是**奇数**（配置校验直接拒绝偶数，避免平票）。

### 3.3 复制状态机

统一抽象成**按命名空间分区的 KV**：

```
Key   = "<ns>/<key>"        ns ∈ {task, quota, audit, oidc, abac, cfg, ...}
Value = 长度前缀 + 载荷（各命名空间自有编码）
```

- 各模块只依赖三个原语：`put(ns,key,value)` / `delete(ns,key)` / `get(ns,key)`；
- 所有写入都经 Raft 日志 → 状态机 apply，**先写日志再应用**；
- 读：leader 强一致（本地 apply 索引 ≥ 读请求屏障）；follower 本地读为
  最终一致（仅 UI 概览，响应里带 `stale: true`）。

### 3.4 与现有模块的接线点

| 模块 | 现在 | v0.8 接线 | 一致性 |
|---|---|---|---|
| `taskstore`（任务定义/日志） | 本地 journal | 任务创建/更新走 `task` 命名空间；读取走状态机 | 线性 |
| `taskengine`（状态机/派发） | 本地 | **只有 leader 派发**；状态迁移写 `task` 命名空间 | 线性 |
| `scheduler` | 本地 | leader 独占调度；follower 只 apply | leader 唯一 |
| `quota` | 本地滑动窗口 | 计数写 `quota` 命名空间（提交前预检 + 提交后落账） | 线性 |
| `audit` | 本地 hash 链 | 追加写 `audit` 命名空间，链头随状态机复制 | 线性 |
| `checkpoint` | 本地 | 写入 `task` 命名空间 | 线性 |
| `oidc` session/state | 本地内存 | 写 `oidc` 命名空间；**state 一次性语义跨节点生效** | 线性 |
| `abac` / `guardrails` 策略 | 配置 | 配置变更写 `cfg` 命名空间并复制 | 线性 |
| `gitops` | 本地 watch | **只有 leader 执行 apply**（避免多节点重复 apply） | leader 唯一 |
| `circuit` / `chaos` | 本地 | 保持本地（运维注入，故意不复制） | 本地 |
| `peer` 拓扑 / `lease` / `slo` | 本地 | 保持本地 | 本地 |
| `license` | 本地文件 | 保持本地（离线签发，按节点授权） | 本地 |

> **要点**：OIDC 浏览器 session 的多副本共享是本波最直接的收益——滚动升级
> 不再掉线、login 与 callback 可落在不同副本。

### 3.5 成员变更

- 采用 **joint consensus**（Raft §6）：先进入过渡配置（旧+新共同决策），
  再切到新配置，避免成员变更期间出现两个多数派；
- 一次只允许一个成员变更在途；
- learner → voting member 的提升走 joint consensus；
- 成员列表持久化在状态机（`cfg/members`），不依赖配置文件（配置文件只是
  首次引导的种子）。

### 3.6 传输与安全

- 复用既有 peer WebSocket（`/peer/ws`，cluster_token 校验，mTLS 可选）；
- 新增帧：`kind="ctrl"`, `action ∈ {ha_vote_req, ha_vote_resp, ha_append,
  ha_append_resp, ha_install_snapshot, ha_install_snapshot_resp, ha_read_index}`；
- **旧节点零破坏**：conn 底部分支对未知 `ctrl` 帧直接忽略（既有语义）；
- 帧体走 `Envelope.payload`（JSON），大快照走二进制分片（沿用
  `Frame::Binary` 通道），单片上限 1 MiB。

### 3.7 持久化

```
<data_dir>/ha/log-<node_id>.bin     追加日志（长度前缀 + CRC32C + 记录）
<data_dir>/ha/snapshot-<node_id>.bin 状态机快照
<data_dir>/ha/state-<node_id>.json   term / voted_for / commit_index（原子写）
```

- 追加写：每批 fsync（默认 `ha.fsync = "batch"`，可选 `always`）；
- 状态文件原子写（temp + fsync + rename），与 v0.6.1 身份锚点同一纪律；
- 日志损坏：CRC 校验失败即截断到最后一个完整记录（fail-safe：宁可少日志，
  不可用坏日志）。

## 4. 配置（向后兼容，serde-default）

```jsonc
"ha": {
  "enabled": false,                    // 缺省关闭 → 行为与 v0.7 逐字相同
  "cluster": [],                       // 初始成员 "node_id@host:port"
  "voting_members": [],                // 奇数，≤9；缺省=全部 cluster 成员
  "learners": [],                      // 只复制不投票
  "election_timeout_ms": 1000,         // 300-5000，随机化 ±40%
  "heartbeat_interval_ms": 200,        // 50-1000
  "max_inflight_append": 64,           // 流控
  "snapshot_threshold_entries": 10000, // 超过即快照
  "apply_batch_size": 256,
  "read_consistency": "leader",        // leader | local
  "fsync": "batch"                     // batch | always
}
```

校验规则（`Config::validate`）：

- `enabled=true` 时 `cluster` 非空，且每项形如 `node_id@host:port`；
- `voting_members` 必须为**奇数**且 ≤9；`voting_members ∪ learners` 覆盖
  `cluster`；
- 自身 node_id 必须在 `cluster` 中（否则拒绝启动，避免孤立节点自任 leader）；
- `election_timeout_ms > heartbeat_interval_ms * 3`；
- 缺省段 = 不存在该段时全部取默认值（老配置零变化）。

## 5. API

| 端点 | 角色 | 说明 |
|---|---|---|
| `GET /v1/ha/status` | Viewer | role / term / commit_index / applied_index / 成员 / quorum / 是否降级 / 状态机键数 |
| `GET /v1/ha/log?from=&to=` | Admin | 复制日志分页（调试） |
| `POST /v1/ha/snapshot` | Admin | 手动触发快照 |
| `GET /v1/ha/metrics` | Viewer | 选举次数、复制延迟、提交延迟、重试次数 |

## 6. 失败场景矩阵

| 场景 | 期望行为 |
|---|---|
| leader 崩溃 | 新 leader 在 `election_timeout` 内选出；已提交日志保留；未提交丢弃 |
| 少数派节点隔离 | 隔离侧无 quorum → 写入 503 + 进入 degraded 只读；恢复后追日志 |
| 网络分区（3/5 分） | 分区内多数派一侧继续服务；另一侧降级；不出现双写 |
| 磁盘满 | 日志写失败 → 停止接受写（fail-closed）+ 告警；不吞错 |
| 时钟偏移 | Raft 不依赖物理时钟（超时用本地单调计时 + term 兜底）；审计时间戳仍用墙钟 |
| 成员变更中途崩溃 | joint consensus 保证不出现两个多数派；重启后按持久化成员列表继续 |
| 节点重启 | 重放日志 + 加载最近快照；`applied_index` 追平后恢复服务 |
| 老版本节点混入 | 不识别 `ha_*` 帧 → 忽略；不参与选举；行为与今天一致 |

## 7. 降级策略（与 v0.7 既有降级模式统一）

| 条件 | 行为 |
|---|---|
| `ha.enabled=false` | 完全走 v0.7 路径（现状） |
| HA 开启但未成 quorum | **degraded：只读**（可查不能写），`/v1/ha/status` 明示降级原因 |
| HA 开启且已成 quorum | 正常读写 |
| 快照/日志损坏 | 截断到最后完整记录 + 告警；若无法回放则该副本退出集群（不猜） |

## 8. 分阶段实施

| 阶段 | 内容 | 出口标准（可验证） |
|---|---|---|
| **M0** | 本 RFC + 评审 | 文档定稿，决策点 D1~D8 拍板 |
| **M1** | **传输无关的 Raft 内核**（`src/ha.rs`）：term/vote/log/apply/快照 + KV 状态机 + 内存传输单测 | ✅ 已完成（见 §8.1） |
| **M2** | **接线 peer WS**：`ha_*` 帧、握手、真实多进程选主与日志复制 | 冒烟：3 进程集群选出 leader，提交任务在 follower 可见，leader 挂掉后接管 |
| **M3** | 快照/成员变更/故障注入 | 冒烟：日志截断恢复、joint consensus 成员变更、分区降级 |
| **M4** | **状态迁移**：`taskstore`/`quota`/`audit`/`oidc` 接入状态机；`taskengine`/`gitops` 仅 leader 执行 | 冒烟：滚动升级不掉线；配额全局一致；审计链跨节点连续 |
| **M5** | 商用验收：20 机真机 + 外部用户 5 分钟上手 | 验收报告 + 部署文档 |

M1 明确**不**接网络：`ha` 内核只依赖消息收发接口（内核只产出「发给谁、什么
消息」），用内存实现做单测，M2 再接真实传输——避免在算法未验证前就动线。

### 8.1 M1 交付内容（2026-10-21）

**代码**：`src/ha.rs`（约 1100 行，含单测）

- `RaftNode`：term / role / 日志 / `commit_index` / `last_applied` /
  `voted_for` / `next_index` / `match_index` / 选举计时器 / leader 租约；
- `RaftMessage`：`RequestVote` / `RequestVoteResp` / `AppendEntries` /
  `AppendEntriesResp` / `InstallSnapshot` / `InstallSnapshotResp`；
- `KvState`：按命名空间分区的 KV 状态机（`Put`/`Delete` 幂等）；
- `PersistentState`：term / 投票 / 日志的持久化边界（`persistent()` /
  `restore()`）；
- **pre-vote**：先探票再正式竞选，孤立节点回归时不打断在任 leader，也不
  抬高 term；
- **提交规则**：多数派复制 + 仅当该条 `term == current_term` 才推进
  `commit_index`（Raft §5.4.2）；
- **回退不刷屏**：追加失败时只回退 `next_index`，由下一次心跳重试（避免
  leader 与 follower 互刷死循环）。

**配置**：`agentlink.json` 新增 `ha` 段（serde-default，缺省 `enabled=false`
= 行为与 v0.7 逐字相同）。校验规则见 §4（奇数投票成员、≤9、必须含自身
node_id、超时关系、读一致性/fsync 取值）。

> **M1 安全闸**：`ha.enabled=true` 在 M1 会被 `Config::validate` **直接拒绝**
> （"not implemented yet (v0.8 M2 pending)"）——内核已实现但尚未接入运行时，
> 宁可启动失败也不能让现场误以为已经具备 HA 保护。M2 接线后解除该闸。

**单测**（`cargo test`：**219/219**，新增 12 条）：

| 用例 | 覆盖 |
|---|---|
| `elects_exactly_one_leader` | 3 节点选主唯一、term 一致 |
| `vote_not_granted_twice_in_same_term` | 同 term 只投一票 |
| `candidate_with_stale_log_is_rejected` | 日志落后的候选拿不到票 |
| `replicates_and_applies_to_all_nodes` | 复制 + 按序 apply + 删除 |
| `new_leader_keeps_committed_entries` | leader 隔离后新 leader 接管、旧 leader 回归被纠正 |
| `minority_partition_cannot_commit` | 少数派分区不得提交（不脑裂双写） |
| `conflicting_suffix_is_overwritten` | 冲突后缀被 leader 覆盖 |
| `snapshot_install_restores_state` | 安装快照恢复状态机 |
| `pre_vote_does_not_inflate_term_of_isolated_node` | pre-vote 不抬 term |
| `persistent_state_survives_restart` | 持久化边界 |
| `kv_state_machine_basics` | KV 状态机 |
| `validate_ha_config_rules` | HA 配置校验规则 |

**回归**：OIDC 三波 14/14 + 12/12 + 9/9、WS 5/5、配额 7/7、chaos 6/6；
`cargo fmt --check` / `cargo clippy -- -D warnings`（default + `--features mdns`）全绿。


## 9. 验证方案

1. **单测（M1）**：内存传输模拟 3/5 节点；覆盖选举安全性（单 term 一票、
   投票日志新旧约束）、日志匹配回退、提交规则（仅当前 term 可直接提交）、
   apply 顺序与幂等、快照/安装快照、重启恢复。
2. **线性一致性检查（M2+）**：写操作带唯一 id，记录各节点观察顺序，检查
   全序一致（参考 Jepsen 思路，先做「单写多读 + 历史校验」的轻量版）。
3. **故障注入（M3）**：复用既有 `chaos` 思路（分区、延迟、进程 kill、磁盘满）。
4. **回归矩阵**：既有 6 套冒烟 + 单测全绿；`ha.enabled=false` 时行为逐字
   不变（新增「默认态等价」用例）。
5. **真机（M5）**：20 台机器、拔电/断网/磁盘满、滚动升级。

## 10. 风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| 自研 Raft 实现出错 | 数据不一致 | M1 先做内核 + 单测；M2 才开始接线；默认关闭 |
| 全量复制带宽 | LAN 压力 | learner 只收不投；批量 apply；快照压缩 |
| 状态机迁移改动大 | 回归面爆炸 | 逐模块迁移（M4 拆成 4 个子包），每包独立冒烟 |
| 脑裂双写 | 配额超发/审计乱序 | 写入必须经 quorum；无 quorum 一律 503 + 只读降级 |
| 磁盘/IO 成为瓶颈 | 吞吐下降 | 批量 fsync（`fsync=batch`）+ 快照压缩 + 预留空间告警 |
| 与 v0.7 既有降级/混沌语义冲突 | 行为不一致 | HA 降级直接复用 degraded 语义，不另起炉灶 |

## 11. 决策记录（ADR）

- **ADR-01 内嵌 Raft 而非外挂共识服务**：单二进制 + 零运行时依赖是产品铁律；
  20 台规模的自研 Raft 复杂度可控（无成员变更前约 1500 行）。
- **ADR-02 KV 状态机而非复制文件/数据库**：文件复制需要处理并发写与幂等
  恢复，KV 状态机让「复制」与「业务语义」解耦，模块改造成本最低。
- **ADR-03 投票成员 ≤9 + learners**：全量 20 节点投票会让每次写放大 20 倍，
  且 learner 扩容不影响 quorum。
- **ADR-04 复用 peer WS 传输**：不新增端口/证书/心跳，故障面最小；未知帧
  忽略保证旧节点零破坏。
- **ADR-05 读默认强一致**：配额/任务状态读到旧值会直接导致业务错误
  （超发、误判完成），代价（读延迟）可接受。
- **ADR-06 默认关闭**：`ha.enabled=false` 时 v0.8 与 v0.7 行为逐字相同，
  现场升级零风险。
